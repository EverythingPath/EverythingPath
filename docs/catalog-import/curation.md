# Note curation operators

`catalog:curate` drafts content-bound records; `catalog:preview` applies them and evaluates coverage together with attribution admission. This workflow prepares catalog content locally. It does not publish a release or change a Character Sheet.

## Commands

Use clean checkouts at the catalog pins. Both commands verify Git identity and the manifests. `--allow-unverified-checkouts` is the explicit fixture/development override; reports record it and it does not bypass either coverage or attribution admission.

```sh
# Full corpus (no batch bound)
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --out .scratch/catalog-curation/full-drafts
# One curation batch
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --out .scratch/catalog-curation/drafts
pnpm -s catalog:preview --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --curation .scratch/catalog-curation/drafts/records.json --out .scratch/catalog-curation/preview
```

The default input overlay is [`scripts/catalog/reviewed-curation.json`](../../scripts/catalog/reviewed-curation.json), beside reviewed identity remaps. Content batches contribute their reviewed records there. An alternative file is supplied with `--records` to the drafter or `--curation` to preview. Commands reject source-overlapping output paths, unrelated output files and symlink report files before writing. A drafter can resume into the same directory when its `--records` is exactly that directory's regular `records.json`.

For a curation ticket, pass `--candidates path/to/keys.json` to both commands. The file is a JSON array of exact upstream keys, including any folder/excluded records in the ticket inventory. A selection accepts at most 100 unique keys and three class definitions; unknown keys are rejected. Without `--candidates`, both commands run over the complete import with no batch bound, as for a full drafter run or full preview. Source verification, source fingerprints, identity resolution and helper lookup still use the complete pinned checkouts. Reports include `candidateKeys`; inventory counts and `coverageComplete` describe only that selection. A bounded preview does not admit linked entries outside the selection: their absence can produce reference failures. Run a full preview as well to distinguish these from failures present in the complete import. This selector does not publish a release or establish whole-corpus coverage.

The drafter writes `records.json` in the canonical overlay form (see [Parallel batches](#parallel-batches)) and `curation.json`; extraction errors and malformed records write no new reports. Its successful exit means drafting completed, even if diagnostics remain. Preview writes `catalog.json`, `comparison.json`, `unsupported.json`, `curation.json` and `admission.json` before exiting nonzero for a coverage/admission failure. Named attribution holds remain holds. A missing curation record or unresolved curation mechanics never hold or fail a candidate's row: they label it unverified ([#227 rule](#the-227-admission-rule)).

## Record contract

A record has `externalKey`, `kind`, `target`, `text`, `textSha256`, `status`, `outputs`, `rationale`, `diagnostics` and `seedBindings`. The strict schema and inferred TypeScript types live in [`scripts/catalog/curation.ts`](../../scripts/catalog/curation.ts). Identities use the reviewed remap's retained external key before matching. Repeated text on another entry never shares a record.

- `note` binds the Foundry target and exact raw note string, before sanitization. `textSha256` is SHA-256 of those UTF-8 bytes.
- `conditional` binds `actionId` and `conditionalId`, the ordered Foundry `target/subTarget` values, and the entire serialized conditional (name, formula, critical mode, damage type and other mechanics). The exact serialized payload is stored as `text`; its hash is calculated the same way. Reordering actions with stable IDs preserves bindings. A record without IDs falls back to position, so reorder requires fresh drafts.
- `itemAbility` binds the exact raw imported description, even when the ability has no notes or conditionals. Helper seed dependencies retain their own complete bindings, so changed helper mechanics invalidate a seeded draft even when the ability's description stays the same.
- `description` binds the raw description but belongs to the separate prose pass, outside the required note gate.

The output list contains strict discriminated variants:

| `kind`        | Output                                                                                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modifier`    | Closed runtime target/bonus type, finite number or `{ formula }`, optional condition and `stacksWithinEntry: true`.                                                       |
| `note`        | Plain text for rules not represented by structured output, optional closed target and Situation; absent target means entry-level text.                                    |
| `itemAbility` | `bonusEquivalent`, `damageDice` (`dice`, `on: hit/crit`, `damageType`, optional Situation), `doublesThreat`, `weaponDamageTypes`, `choice: creatureType`, or `sourceKey`. |

Modifiers append to the entry's `modifiers`. A race's record can apply to one of its standard Racial Traits instead: a note record goes to the trait whose note covers the same statistic, and the reviewed description re-homes move named outputs (see [Racial Trait Grants](README.md#racial-trait-grants)). The record still binds to the race's raw text. While the race's note record is checked, it stands in for that trait's own notes on the target that state the same numbers: they are not required inputs, the drafter does not draft them, and an existing draft for one is reported stale. Only a checked note record of the trait for the target supersedes the race's note: the race's note is then no longer a required input and its record is reported stale. A full drafter run therefore retires none of the checked race records. Before checking a trait's note record, check that it covers the race record's reviewed outputs; once it lands, remove the stale race record. Also check the import report's `latentOverlaps`. When an output's owning trait is outside the extraction, the output is not applied and the race reports it as a `curation.home` unsupported issue. Outside these cases, outputs apply to the record's own entry; Notes append sanitized plain text to `situationalNotes`. Foundry inline-roll delimiters and roll commands are removed, and formula references become readable labels (for example `+[[@resources.rage]]` becomes `+rage`); no expression is executed. Item Ability mechanics enrich `detail.kind: itemAbility`, using the data model's names, and damage dice from multiple outputs are preserved in order. A die may carry a shared, local or option Situation, and `foeEnhancement` sets how much better the weapon's enhancement is against the designated foe; an Item Ability record's Modifier may read `@item.enhancement`, the enhancement of the item part listing the ability (#764). Structured Item Ability mechanics do not produce duplicate description Notes; only uncovered nonnumeric rules remain Notes. `sourceKey` belongs to the common entry. Weapon/action Modifiers use `condition.weapon: '$self'`. A Modifier without a weapon condition, such as Shadow's Stealth bonus, follows the active item. The existing sheet resolver consumes the numeric/formula Modifier shape; attack and Item Ability consumers implement their model-specific weapon/dice/choice behavior in their own tickets.

An intentional `outputs: []` means explicit covered/no-output, with a nonempty rationale explaining what other record supplies the behavior. A prose draft that cannot be parsed can also have no outputs, but its review diagnostic means it is pending review rather than deliberately covered. Duplicate bindings, unknown output properties/targets/bonus types, mismatched text hashes and malformed review metadata are rejected. Unresolved numeric/action/helper Notes use the reserved text `Review required: replace this placeholder with readable rules text or structured outputs.` instead of raw mechanics or serialized conditionals. Checking a record or removing its diagnostics while that placeholder remains is rejected; replace the output with readable rules text, structured mechanics or deliberate covered/no-output first.

Both `drafted` and `checked` records apply under #228. The #303 workflow adds a conservative exception: drafted records carrying any diagnostic contribute no output until checked. Each diagnostic has `{ kind: 'unresolved' | 'review', text }`; its wording does not determine behavior. `checked` requires `reviewedBy` and a valid `reviewedOn` date. Check against the imported description and record the reason; this is distinct from the Attribution Assessment and does not establish permission or book-level attribution. Only checked records may set `stacksWithinEntry`. The drafter flags “stacks with” for review and never sets it itself. Curation status remains operator data.

Shared Situations are declared in `situations` with `key`, `label`, exact case-insensitive `aliases`, reviewer and date. Only those reviewed aliases map automatically; ambiguous/new wording stays local. Unknown shared keys are rejected, including keys in Item Ability dice. Keys are flat and imply nothing else. Promote a local Situation deliberately when a second entry names it.

## Draft, review and resume

The parser handles leading inline/plain numeric notes, several numeric clauses, multi-situation notes, recognized targets, granting-class formulas, readable prose Notes, action numeric conditionals, and bounded Item Ability patterns. The named Common Conditional Modifiers and Weapon Enchant Conditional Modifiers helpers remain excluded from catalog entries and the coverage requirement. The second helper supplies seeds to abilities matched by name; hit/critical dice remain distinct.

Conservative drafts preserve candidate outputs and diagnostics for mechanics the parser cannot complete, but diagnosed drafts do not apply them. Metadata such as an ability's price never covers an unparsed numerical effect. Target-dependent helper abilities require an operator to provide their Situation/choice rather than applying unconditional damage. Unsupported note formulas retain runtime-shaped candidate contributions, with readable Note text and a review diagnostic. The draft is held until checked; once checked, its unsupported formula warning remains and the formula contributes nothing, preserving #228's runtime behavior. The closed parser is reused; no Foundry expression is executed. Rewrites beyond supported variable mappings, such as complex `if(gte(...))` formulas, must be drafted into the closed arithmetic grammar by the operator.

The named Item Ability policies live in [`reviewed-item-ability-policies.json`](../../scripts/catalog/reviewed-item-ability-policies.json), beside the overlay. Each policy cites the exact offline pf1-content 11.4.0 data path, pinned commit and upstream book/page metadata, with a review rationale and date. The table supplies Speed's shared haste Source and the target-dependent helper holds. Draft rationales include the relevant citation. This parser-policy review used local pinned descriptions, without a network lookup or printed-book verification, and does not establish an Attribution Assessment or complete content review.

Read `diagnostics` and compare every output with the imported description. Complete or correct the outputs, clear resolved `unresolved` diagnostics, supply an explicit covered/no-output rationale where appropriate, and mark checked when reviewed. A diagnosed drafted record for a required note, conditional or ability fails coverage even though its binding exists and is not listed as missing. Checked records apply their outputs for either diagnostic kind; retained `review` diagnostics do not fail coverage, while retained `unresolved` mechanics still do (coverage is the import's `curation.passed`; admission only labels the row). Prose-pass diagnostics appear in `unresolvedDescriptions` and remain outside the required gate.

Resume supplies the existing file:

```sh
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --records .scratch/catalog-curation/drafts/records.json --out .scratch/catalog-curation/drafts
```

Valid existing drafts, checks, rationales and outputs are retained. Only absent exact bindings are added. An unchanged rerun writes identical records and adds none. Changed source text/target produces a fresh record and the old binding is reported stale; it never applies. Changed helper seeds replace only the unusable seeded record, reporting `replaced` and resetting its status to drafted. Description/seed disagreements remain unresolved. Removed or retargeted records on present entries are stale; records for entries outside this import are `unused`, not falsely stale.

The prose-only pass visits description candidates containing “vs.”, “against” or “when”, independently of the note requirement:

```sh
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --records .scratch/catalog-curation/drafts/records.json --descriptions --out .scratch/catalog-curation/prose
```

It can produce ordinary overlay Modifiers. Unparsed or partially parsed prose receives a review diagnostic and no applicable draft output; it does not fall back to making the entire description a Note. Review and supply explicit outputs before checking it. Optional prose diagnostics do not turn a candidate into a missing-note failure. Reruns add only missing description bindings.

## Reports and the bounded demonstration

`curation.json` itemises `missing`, `stale`, `unused`, `applied` records by status, `unresolvedMechanics`, `unresolvedDescriptions`, and summary counts. `summary.required`, `drafted`, `checked` and `missing` count only required notes, action conditionals and Item Abilities. `summary.descriptions` reports optional prose candidates and their drafted/checked matches separately; prose diagnostics never fail the required gate. Held diagnosed drafts appear in the unresolved lists and matched status counts, but not in `applied`. Draft reports also list `added`, `replaced`, input verification/fingerprints and the canonical records fingerprint. Preview's admission report contains the coverage report and, on each admitted row with a missing record or unresolved mechanics, its curation gaps (`unverified`, [#227 rule](#the-227-admission-rule)); its extraction fingerprint covers applied outputs and curation report. A changed output therefore invalidates existing attribution content bindings.

[`tests/fixtures/curation`](../../tests/fixtures/curation/README.md) commits synthetic category fixtures, two real excluded helpers, initial drafts, the optional prose pass, fixture-only checked/no-output examples, gap-only resume, missing and covered preview reports, and the deterministic public import artifact. Observed command statuses and counts are in [`observed.json`](../../tests/fixtures/curation/observed.json). The tests exercise exact invalidation, raw sanitizer-equivalent changes, stable action IDs, identity remaps, partial resume, helper-only changes, schema rejection, unsupported formulas and real sheet calculation.

This establishes the workflow and bounded coverage gate for #303. It does not curate the upstream corpus, review real content records, complete per-entry attribution, or meet CRB launch review. The enumerated content batches own those steps and commit their own records and reports at each pin bump.

## Structure records (#716)

The archetype and prestige class import from PCGen and the PRD ([#716](https://github.com/AndreasUnunger/EverythingPath/issues/716)) reviews structure by hand before any mapper runs. Its records live in the overlay's `structures` collection, beside the note records; the schema, the gate and the application are in [`scripts/catalog/structure-curation.ts`](../../scripts/catalog/structure-curation.ts).

A structure record binds one entry, a set of its fields and the hash of the upstream records it was reviewed against, and names the review items it settles:

- `externalKey` is the entry's catalog key, usually `everythingpath/<id>`.
- `sourceSha256` comes from `hashStructureSource`: the SHA-256 of the entry's upstream records in merge order, each as its upstream key (`pcgen:<file>#<KEY>` or `prd:<path>#<id>`) and raw text. A PCGen entity is its record line and its `.MOD` lines (a prestige class: its `CLASS:` lines, its level lines and its applied `.MOD` lines); a PRD section is added when one supplies a field. It takes at least one record. Line numbers aren't hashed, since only the KEY is stable. Archer's hash covers `apg_abilities_class.lst:2102` and its `.MOD` line at `:3667`.
- `fields` maps each bound field to its reviewed value. A field is an imported entry field, such as `situationalNotes` or `sources`, or a property of a detail kind, such as `detail.featuresByLevel`. The entry's identity (`externalKey`, `upstreamKey`, `pack`), the whole `detail`, `detail.kind`, `provenance`, `unsupported` and `attributionFrom` can't be bound, and an unknown field such as `detail.parentFeatre` is rejected with the overlay.
- `resolves` lists the review items the record settles, each as `{ kind, id }`: a mapper item's kind and its identity among that entry's items of the kind (for example the PCGen token that raised it), or `{ kind: 'ownedFeature', id: <feature locator> }`.
- `noMechanics: true`, with empty `fields`, is the reviewed disposition that an owned feature has nothing to structure, such as Archer's Safe Shot: not provoking attacks of opportunity with a bow isn't calculated on the sheet. It settles only the owned features it names in `resolves`, never another kind of item.
- `status`, `rationale`, `reviewedBy` and `reviewedOn` work as for note records: `checked` needs a reviewer and date. A record is written `drafted`; a checked one also names in `receipt` the review that confirmed it, which binds its values and `resolves`, and only the orchestrator's record step marks it checked ([Review receipts](README.md#pcgen-sources-716), #757). The receipt check catches unreviewed or accidental `checked` claims, not a determined forger: run directories are ordinary writable files, so only the orchestrator runs the record step, and workers never do.

Records of one entry and hash bind disjoint field sets and settle each item at most once, and a `noMechanics` disposition is the only record for its entry and hash; the overlay is rejected otherwise.

**Application.** A checked record replaces the mapper's output for its bound fields on every entry with its key and source hash, and each replaced field's `provenance` names the record (`{ source: 'overlay', locator: { externalKey, kind: 'structure', target: <field> } }`). Before anything applies, each field must exist on the entry's detail kind and each value must parse unchanged against the imported entry schema: `name: null`, `sources: 0`, a source with a `page` instead of `pages`, or `detail.featuresByLevel` on a class feature fail as `invalid`. A drafted record applies nothing. When the entry's current hash differs from the record's, the record is `stale` and applies nothing: a changed PCGen line, a newly merged `.MOD` line or a PRD section added to the entry all reopen its review. Records for entries outside the import are `unused`.

**Source variants.** Same-key variants in different books stay separate entries with their own hashes (plan §5), so each variant's records apply only to that variant: ISWG's `Lawbringer ~ HK` can take its p.279 citation while AG's keeps its own. When records of two variants of one key bind the same field, they compete. A checked same-identity decision in the identity ledger settles that when it is current, every record it reviewed present at the hash it bound (#716 P6), and its `sources` include every competing variant: the variant it takes `mechanicsFrom` applies and the others are `superseded`. A change to any reviewed record, the superseded one included, makes it stale. Without one, or when a competing variant isn't among the decision's sources, the competing records apply nothing and the entry is held with a `conflicts` entry.

**Coverage gate.** The mappers hand to review what they can't decide: an unmatched replacement, an unchecked casting change, an unchecked requirement, a variant, a conflict, a Product Identity flag, an option or an unsupported kind. The archetype mapper also says where the archetype's own text disagrees with its output (`altersText:<feature>`, `textReplaces:<feature>`, and `altersText:sentence:<holder KEY>#<n>` or `textReplaces:sentence:<holder KEY>#<n>` for a sentence it can't attribute to one feature; [README](README.md#pcgen-sources-716), "Archetype mapper (P5)"), so such an archetype is held until a checked record that binds the fields the item names settles it, and names each granted record it neither emits nor reads (`unemittedGrant:<KEY>`, with the tokens it drops), which a checked record naming it settles. The prestige mapper (P4) raises an `uncheckedRequirement` for each requirement it leaves as an `unchecked` clause (its id is the PCGen token; the whole tree has 97), so a prestige class with readable but unchecked prose can't pass until a checked record that binds `prerequisites` settles each one. It also raises a `conflict` for each named requirement exception and PCGen data error, an `uncheckedCasting` for each advance the casting model can't express, `productIdentity` for NAMEISPI and `option` for a Pathfinder Society record. Each review item needs a checked record on its entry and hash that names the item's kind and id in `resolves`; an unrelated checked record doesn't settle it. When the item names fields, the settling record must bind them. Every feature record an archetype or prestige class grants directly needs a checked record naming it as an `ownedFeature`, with reviewed fields or a `noMechanics` disposition, so no feature passes unreviewed. Owned features count by locator: a same-key variant in another book (ISWG's and AG's `Discipline ~ HK`) has its own hash and needs its own record, and a feature two owners share needs one. An entry with an unsettled item, an unreviewed owned feature, an invalid record or a variant conflict is `held` and counted as hand review; the gate passes only when nothing is held. The report lists `held`, `handReview`, `unreviewedFeatures`, `invalid`, `conflicts`, `applied`, `superseded`, `stale` and `unused`, with counts in `summary`.

**Batches.** Each #716 batch ticket (#659–#702 for archetypes, #551–#576 for prestige classes) names its owners with an Import selector, such as `{"source": "#716 PRD/PCGen import", "kind": "archetype", "base_class": "alchemist", "max_candidates": 100}` or `{"source": "#716 PRD/PCGen import", "kind": "prestige", "name_initial": "A", "max_candidates": 100}`. `planImportBatches` in [`scripts/catalog/import.ts`](../../scripts/catalog/import.ts) picks the owners out (archetypes by PCGen's base class, which every archetype owner must name, prestige classes by the initial of their name), orders them by name and then locator, and packs them into ordered sub-batches of at most `max_candidates` keys, never over 100. A sub-batch counts each owner and each distinct feature record its owners grant directly, by locator; nested grants are reviewed with their owner and aren't counted. An owner and its features always share a sub-batch, so a feature two owners in different sub-batches share counts in each. APG's twelve fighter archetypes and their 86 directly owned features fit one batch of 98 keys. In the full PCGen inventory the fighter's 62 archetypes and 347 features take five sub-batches. A batch ticket curates its first sub-batch and reports the rest as separately reviewable overflow. A prestige class is a class definition, so a prestige sub-batch also holds at most three prestige records, the bound `--candidates` enforces. Records count separately, variants included, and same-name variants share a sub-batch where they fit: the three Pathfinder Savant records fill one. In the full PCGen inventory the 99 prestige records take 40 sub-batches over 18 initials. Archetype sub-batches select no class definitions and keep only the key limit.

The PCGen reader (#716 P3) and the mappers (P4, P5) supply the entries, their hashes, the review items and the owned features. The prestige mapper (`mapPrestigeClass`, [`scripts/catalog/pcgen/prestige.ts`](../../scripts/catalog/pcgen/prestige.ts)) supplies a prestige class's entry, hash and review items; the import emits a selected prestige class's owned features as feature entries beside it (#716 D1, [prestige classes](prestige-and-unchained.md#imported-prestige-classes-dragon-disciple-716-d1)), each an owned feature of the class. The archetype mapper (`mapArchetype`, [`scripts/catalog/pcgen/archetypes.ts`](../../scripts/catalog/pcgen/archetypes.ts), P5) supplies an archetype's entry, hash and review items, a class feature entry and hash for each feature it owns directly, and those owned features; review items about one owned feature, such as Dandy's Cold favored terrain, sit on that feature's entry, while Archer's Weapon Mastery is held on the archetype until a checked record binds its addition level and its alteration (`detail.adds`, `detail.featureChanges`). An archetype that changes the class skills says so on its entry (`detail.changesClassSkills`, also where no added or removed skill is recorded), and two such archetypes of one class raise no review item and may be selected together: the sheet warns the Character who takes both on the class skills' feature identity ([archetypes](../character-sheet/archetypes-and-prestige-classes.md); rotation-3, root decision 2026-11-17). A structure record therefore names no pair; one that settles an archetype's own `classSkills` or `classSkillsBase` item binds `detail.classSkillsAdded` and `detail.classSkillsRemoved` as before. The import applies and reports them for the chosen archetypes and prestige classes it emits with `--pcgen` (`catalog:preview`, `catalog:release build`; [README](README.md#pcgen-sources-716), "Import emission"); `catalog:curate` accepts an overlay with structure records but doesn't draft, apply or report them, and a drafter's `records.json` carries note records only.

## Rule-value records (stats-d1)

A rule value ([GLOSSARY](../../GLOSSARY.md), [Rule values](../character-sheet/rule-values.md)) is a number no import reads, such as Channel Energy's dice or the Mad Dog's damage reduction. A rule-value record gives one entry its rule values, in the overlay's `ruleValues` collection beside `structures`; the schema and the applier are in [`scripts/catalog/curation.ts`](../../scripts/catalog/curation.ts) (`ruleValueRecordSchema`, `applyRuleValueCuration`).

- `externalKey` names the entry: a Foundry entry such as `pf1/kXXz1lO4i7CibHJ9`, or an `everythingpath/` one such as `everythingpath/barbarian-mad-dog-damage-reduction`. One record per entry and **group** (stats-d3): its dice, dice increases (`diceIncrease`, rotation-5), damage reduction and spell resistance in one record (the "other" group), its per-day values (`dailyMaximum`, `dailyMaximumIncrease`) in another, so an entry with checked dice can gain a drafted per-day record without its dice going back to drafted. A second record of a group is refused with the overlay, and so is a record mixing the groups.
- `descriptionSha256` is the SHA-256 of the entry's imported `description`, the text the values were reviewed against: after sanitizing and, for a PCGen entry, after its checked structure records.
- `outputs` holds the curation output kind `ruleValue`, `{ kind: 'ruleValue', ruleValue }`, one per rule value: one to 16, each as `ruleValueSchema` takes it, the whole list as `storedRuleValuesSchema` does, so the limits are the stored entry's (a formula of 4,096 characters, a bypass of 64), and an increase's `oncePerSource` and `choice` and a maximum's `joins` (rotation-6) are taken on the kinds that take them there and refused on the others ([Increases](../character-sheet/rule-values.md#increases-once-per-source-a-choice-not-counted-rotation-6), `tests/catalog/rule-value-curation-rotation-6.test.ts`); no committed record carries them. A malformed value refuses the overlay; nothing is dropped. Only a rule-value record carries the kind: a note record's outputs can't, since its drafted outputs apply.
- `status`, `rationale`, `reviewedBy`, `reviewedOn` and `receipt` work as for structure records: the record is written `drafted`, and only the orchestrator's record step marks it checked under a review receipt (#757). `catalog-record-review.ts --list` prints it as `rule-value <externalKey> sha256:<descriptionSha256>`, a per-day record as `rule-value <externalKey> per-day sha256:<descriptionSha256>`; the receipt covers its outputs.

**Application.** The import applies the records after the structure gate, to the Foundry and PCGen entries alike. A checked record sets the `ruleValues` of the entry with its key and of no other (an entry with a checked record of each group gets both records' values, in record order, the per-day record after the other one; a drafted record contributes nothing: [Two records on one entry](#two-records-on-one-entry-stats-d3)): a schedule increment shares its parent's upstream record but is its own entry, and the sheet counts it as a row instead ([Amounts](../character-sheet/rule-values.md#amounts)). An `everythingpath/` entry's `provenance.ruleValues` names the record. A drafted record applies nothing and changes no entry. The import gives no entry rule values of its own, so an entry already carrying other values is refused, never overwritten, and applying twice gives the same entries and statuses. The release build stores the values in the entry's definition, as the imported entry schema takes them.

**A record that cannot apply refuses the build (fix r1).** Each record gets a status in the curation report's `ruleValues`, in record order: `applied`, `drafted` (applies nothing), `omitted` with the reason the scope being built leaves its entry out, `not-established` (fix r2, below), or `refused` with the reason it cannot apply. A refused record is an admission failure (`Refused rule-value record: <reason>`), as a curation gap naming no candidate is, so the preview writes its reports and exits 1, and the release build fails naming it. The preview's `curation.json` and `admission.json` and the release's `curation:ruleValues:<n>` report rows save the statuses; an overlay without the collection has none.

- **Refused:** a checked record bound to another description (the reason gives both hashes; the entry also gets one `ruleValues` unsupported issue, however often the record is applied); a checked record that cannot apply beside its entry's earlier applied record (stats-d3 fix r1, [below](#two-records-on-one-entry-stats-d3)); a record, drafted or checked, naming an entry the import lacks that no scope leaves out: an `everythingpath/` key the identity ledger (`everythingpath-identities.json`) doesn't have, a Foundry record the inputs have but the import doesn't emit, or any key the whole pinned corpus lacks.
- **Omitted, how the import knows:** a Foundry entry the inputs have outside the curation batch's candidate keys or the release scope; a ledger entry when the import emits no PCGen, its release scope doesn't name it, or it narrows the owner selection. Omitted always means the build shows the exclusion.
- **Not established (fix r2):** a checked record naming an entry that inputs not verified as the whole pinned corpus lack, where the whole corpus would refuse it. Every caller that reads verified checkouts passes `wholeCorpus` from `verifyInputs`: the preview, the release build and curate when they verified theirs, and the launch verification build, the party scope, the #227 matcher and the gate-host Modifiers audit (`launch-modifiers-canonical.test.ts`), which require them (stats-d2 fix r3 and r4; [`verified-import-callers.test.ts`](../../tests/catalog/verified-import-callers.test.ts)). The option is required, with no default (fix r4): every caller of `importCatalog`, `draftCatalogCuration` and `draftCatalogCurationWithReport` states whether its inputs are the whole verified corpus, so the type check refuses one that leaves it out; with `false` (`--allow-unverified-checkouts`, a test's pinned files) the inputs may be a partial tree, so a typo can't be told from a file the tree leaves out, and the build shows neither. The build goes on, so a fixture build keeps working, but the artifact can't reach production: an unscoped artifact has no scope report, and a scoped build gives the scope one `rule-value-not-established` finding per such record (`ruleValueScopeFindings` in [`rule-value-status.ts`](../../scripts/catalog/rule-value-status.ts), read by both `campaign-mvp-v1` and `campaign-party-v1`), so the scope is FAILED; production activation refuses both. ### Two records on one entry (stats-d3)

An entry with a record of each group gets the values of both when both are checked and applied, in the order the overlay holds them; a drafted record contributes nothing. The formatter sorts a record by its entry's key and a per-day record by `<key> per-day`, so the record of the "other" group (dice, dice increases, damage reduction, spell resistance) applies first and the per-day record's values follow it. Channel Energy has one record of each: its dice record is checked and its per-day record drafted and held, so the committed import gives it its dice alone; were the per-day record checked, its `ruleValues` would be its dice, then its per-day maximum ([`rule-values-d3.test.ts`](../../tests/catalog/rule-values-d3.test.ts) checks both, as committed and checked in memory).

The values of the two meet only in the stored schema (`storedRuleValuesSchema`), whose constraints across an entry's values are the limit of 16 and the dice-increase check (`diceIncreaseConflict`, rotation-5: an entry raises a key's dice once, and never the key of its own dice). Each kind's schema constrains one value alone; the dice-increase check reads only dice and dice increases, both of the other group, so it applies within that group's one record; and no per-day key repeats across the two records, since an entry has one per-day record. So the limit of 16 is the one constraint that can fail between two records of different groups that are each valid alone. `rule-value-curation.test.ts` pins that enumeration, so a constraint added to the list fails it. When two checked records give more than 16 together (each meets the limit alone), the later one is **refused**: `<its ID> cannot apply beside <the earlier one's ID>: together they give <n> rule values, and an entry stores at most 16.` The earlier one still applies, and the refusal fails the preview and the release build as any refused record does; nothing is thrown before the statuses are reported. The record step refuses the same pair (`findRuleValueRecordConflicts`): it does not check a record that cannot apply beside its entry's other checked record, and writes nothing.

## Admission policies

The owner settled two admission policies on 2026-10-13 (#735). They apply to every batch from then on; re-assessing the records held under the old reading stays under #735.

- **Later-book classes don't hold a spell.** A class from a later book in a spell's class list (`learnedAt.class`, such as arcanist, antipaladin or skald) does not by itself justify holding the spell. Decide the spell on the evidence for the spell itself (#735, S-03).
- **CRB feats on original-source evidence.** A CRB feat can be admitted when the evidence supports its mechanics as the original source states them. PCGen needn't reproduce its prose exactly, so a partial PCGen comparison is not by itself a hold reason (#735, S-04).

- **Superseded holds.** The legal batch files stay evidence and are not edited. A `reviewed` exception excludes a key with a stated reason.
- **Broken references that now resolve** (`resolved-reference`). A broken-reference hold (an ID with the `-broken-reference-` segment) whose links an importer fix later resolves stops holding through a `resolved-reference` exception: the key, its batch, the hold ID, the links the hold was raised for (`references`, as the source writes them) and the reason: its own, or the name of a reason the file stores once under `sharedReasons` for the entries that give the same one (`reason: { "shared": <name> }`). On every build the gate reads each reference through the importer's link resolution (`uuidKey`, its reviewed wrong-pack links included) and requires the imported candidate to link that key, in its body or in an embedded copy it keeps as an unsupported value. Otherwise the rule decides the row like any other key: its books, its notices and its dependencies (a held dependency still omits it). The schema refuses an entry whose hold isn't a broken-reference hold, an entry with no references, an entry with neither its own reason nor a shared one the file stores, an own reason that another entry or a shared reason already gives, and a shared reason no entry cites. `findResolvedReferenceProblems` refuses an entry whose batch has no record of the key or no such hold, whose record doesn't cite a named reference (by record ID), or whose key keeps another hold. ## Reading a legal record

Code reads a batch legal record (`scripts/catalog/legal/<batch>.json`) through [`legal-records.ts`](../../scripts/catalog/legal-records.ts), by its file name, never by a path: `readLegalRecord('spells-530.json')` for one record, `readLegalRecords(select?)` for a scan of the directory, one `{ name, record }` at a time (`readLegalRecordsIn(root, select?)` for a test's scratch checkout), `legalRecordNamesIn(root)` for the names alone, and `legalRecordSha256(name, root?)` for the digest of the stored bytes, which the notice authority pins. No loader or codec function returns, yields or throws a record's file path, bytes or stored text: `catalog:format` stores the encoded set through `encodeLegalRecordsIn(root)`, which returns the names it rewrote, and a record that cannot be read or parsed is named by its label, quoting neither its path nor its text. A label (`legalRecordLabel(name)`, `scripts/catalog/legal/<name>`) is a reference: the text a message, a report or a hold's evidence names a record by; `legalRecordLabel()` with no name is the directory's (`scripts/catalog/legal/`), as the inventory's #736/#737 owner label uses it. Like any repository path it can be read from the checkout root, so guard 3 limits where it may stand (rule e, below), and what the guard does not see is listed there. A helper that takes a record's name (`readBatchInventory`, `findCommittedBatchOwnershipProblems`, and `readLegalInventory` in `tests/catalog/legal-inventory.ts`, which parses the shape every batch inventory shares: each candidate's key, name and disposition, every other field kept) reads it through the loader, and its module is listed in `legalRecordNameHelpers`; `held-notices.json` is read through [`held-notices.ts`](../../scripts/catalog/legal/held-notices.ts), which parses its whole shape. The loader decodes a record from either stored form ([`legal-record-codec.ts`](../../src/lib/catalog/legal-record-codec.ts)), and a plain record reads as itself, so a reader never parses one with `JSON.parse` or imports it as a JSON module (`legal-records.test.ts`). Every directory scanner reads through the loader: `unwiredLegalRecordScanners` is empty, and guard 3 fails on any module listed there while a record is encoded (rule c). Every other reader reads through it too, but for the modules `legal-record-readers.test.ts` lists, each with what keeps it, and each reads only plain files: hash-bound modules that read only the shared files that are not batch records, tests that read fields only a record's own JSON-module type has, scratch-checkout writers, and writers of shared files that are not batch records. Run with every legal record assumed encoded, guard 3 names exactly those modules (over the same module list as the guard test, [`tracked-modules.ts`](../../tests/catalog/tracked-modules.ts)), so a new bare reader fails there before its record could be encoded.

94 batch records are stored encoded (`encodedLegalRecords`): each repeated entry, then each repeated text, is kept once inside the record's own file. The seven Spells records `spells-530.json` to `spells-536.json` came first (legal-l2: 148,470,593 B / 2,002,093 lines to 24,680,761 B / 487,305 lines); legal-l4 encoded every other batch record whose line count encoding lowers by at least 50 and no test imports as a JSON module, 87 more (145,755,745 B / 2,372,383 lines to 118,367,054 B / 2,080,215 lines): `armors-and-shields-424`, `buffs-547`, `companion-features-505`, `feats-344` to `feats-366`, `items-430` and `-431`, `monster-abilities-506`, `pf-buffs-548` and `-549`, `pf-companion-features-507`, `pf-companions-508`, `pf-special-qualities-501`, `racial-traits-387` to `-404`, `spells-516-evidence`, `spells-527` to `-529`, `spells-537`, `spells-540` to `-544`, `traits-367` to `-386` and `weapons-and-ammo-425` to `-429`.

The others stay plain, each for one reason:

- **A test imports it with its own type** (59: `feats-330` to `-343`, `inherited-notices-264` to `-296`, `races-328`, `racial-hd-329`, `spells-517` to `-526`). 61 tests import one of these as a JSON module and read fields only that record's inferred type has; encoding it would take those types away. Root decision of 2026-11-16; they can follow if those tests are given schemas.
- **Encoding would not lower its line count** (36: `classes-596`, the class-ability records `class-abilities-604` to `-649` but `-619`, and `spells-538`, `-539`, `-546`): its encoded form, with the literal fields in place, is not shorter in lines.
- **It would save fewer than 50 lines** (3: `spells-545`, `class-abilities-619`, `racial-traits-405`): not worth moving its hash.
- **It is not a batch record**: `held-notices.json`, `known-notice-holds.json`, `notice-clearances.json`, `notice-dependency-waivers.json`, the three `section15-*-716.json` files and the two #227 files are shared files, and are not encoded (root decision of 2026-11-16).

The candidate fields listed in `legalRecordLiteralFields` (its identity, disposition, holds, required and inherited-rule notices, comparison and source) stay literal in either form, so `jq` still finds them under `.value.candidates[]`; any other field may be a reference (`{"$entry": id}`, `{"$text": id}`) into `.entries` and `.texts`, review subtrees among them, and a reader of those decodes the record through the loader, as the notice-dependency scanner does (`notice-dependencies.ts` reads the reviews' inherited rules).

**Editing an encoded record.** Never edit the stored form by hand: an entry is shared by every place that names it, and its id is its content's hash. Expand the record, edit the plain form, then format it:

1. `pnpm catalog:format --expand scripts/catalog/legal/spells-532.json` writes the record back in its plain form (the same value, in the `JSON.stringify` layout).
2. Edit it as any plain record.
3. `pnpm catalog:format` stores it encoded again, as every record in the encoded set.

Check 2 (`findLegalRecordProblems`, run by `pnpm catalog:format --check` and `legal-records.test.ts`, "are canonical, decode, and are exactly the encoded set") fails on a record in the set that is stored plain (an expanded record not yet formatted), one that is not its canonical encoding (a hand edit or a reformat), one whose reference does not resolve, whose id is not its content's hash, whose entry or text no reference uses, whose references cycle, or that has a reference in a literal field, and on an encoded record outside the set. Guard 3 (`legal-record-guard.test.ts`) fails on code that names an encoded record anywhere but as a loader function's argument, as described below. A record edit moves its notice-authority input and the identities derived from it, as for a plain record: rerun the [regeneration chain](#parallel-batches) (`prep_regen_steps`: `pnpm -s catalog:launch-legal-authority --write` first, through `--verify --write` and the pin).

The encoding was proven by [`legal-record-proof.ts`](../../scripts/catalog/legal-record-proof.ts) (`node --import tsx scripts/catalog/legal-record-proof.ts --base <commit before the encoding>`), for legal-l2 against `d9a11693` and for legal-l4 against `42d4c790`: each record in the encoded set decodes to the value its previous bytes decode to, every value and key order, and every other notice-authority locator is byte-identical (`legal-record-proof.test.ts`). It compares against the previous representation read from Git, and decodes BASE too, so a record may be stored in either form at BASE; one already encoded at BASE whose value is unchanged must keep its bytes, since its encoding is a function of its value.

`legal-record-guard.test.ts` (guard 3) does not try to prove a read good; it allows one syntactic form in every JS or TS module Git tracks, in every directory and at the root, outside the modules in `legalRecordGuardExemptions` (the loader, its test, the codec, the migration proof and its test, which read stored bytes at two revisions, and the guard's own files), and refuses the rest. (a) A literal naming a record in the encoded set (its name, its repository or `../` path, a URL) stands only as the direct argument of `readLegalRecord`, `legalRecordSha256` or `legalRecordLabel` imported from the loader under its own name, or of a function imported under its own name from a module in `legalRecordNameHelpers`, which itself must not list or read files; anywhere else (a variable, an array, another call, a JSON-module import) it fails, and so does an aliased, default, namespace, dynamic or re-exported import of the loader, or a module declaring a loader or helper name. (b) A literal naming the directory or a path into it fails in a module that also lists or reads files: such a module uses `readLegalRecords()` or `readLegalRecord(name)`. A string, a template's static chunk (its head or a later one) or a `+` operand names it when it holds `catalog/legal` ending the text or followed by `/` (`` `scripts/catalog/legal/spells-${batch}.json` ``, `'scripts/catalog/legal/spells-' + n`, `` `${root}/scripts/catalog/legal/${name}` ``), and so do the arguments `'catalog', 'legal…'`; a relative literal (`./legal/`) is resolved from the module's own directory first. A static import's specifier passes, and so does a complete literal path to one file (`scripts/catalog/legal/held-notices.json`, with nothing appended, or followed by a message's text); rule a covers an encoded name. (c) Every module still in `unwiredLegalRecordScanners` fails. (d) A template or `+` concatenation that could expand to an encoded record's path (its static text holds `catalog/legal`, and what follows matches `/<name>`, each substitution or non-literal operand standing for any text) fails in every module, whether it reads files or not; `legal-record-guard.test.ts` runs it over the tracked code for the encoded set ("no tracked module builds a string that could expand…"), which needs no record read and no other test run. (e) A `legalRecordLabel(...)` call stands only as an element of an array literal, a property value of an object literal, an operand of `===` or `!==`, or a direct argument of `expect(...)` or of a matcher on its chain (`toBe`, `toEqual`, `toContain`, `toMatch`, `toStrictEqual`, `toHaveProperty`); a `+` operand or a template span counts as the string it builds, which must stand in one of those places. Anywhere else (a variable, an assignment, a return value, another call's argument, a spread, the function passed as a value) it fails, even with nothing encoded. An array or object literal holding a label at any depth fails when it is read where it stands: its member or element taken, spread, called, or destructured (`{ … }.evidence`, `[…][0]`, `[…].map(…)`, `const { evidence } = { … }`). An `expect(...)` whose argument holds a label must end in one call of a listed matcher, through `not`, `resolves` or `rejects` only (`.toSatisfy(cb)` and a kept assertion fail). Each failure names `file:line`, the literal and the allowed form.

The guarantee, as root decided it on 2026-11-15 and legal-l2's fix round widened it. Inside it, each of these fails in a Git-tracked JS or TS module outside the exempt ones: an encoded record named by a literal anywhere but as the direct argument of a loader function (or a listed helper's); a legal-directory literal, or a literal path into the directory that is not one complete file path (a template's static chunk or a `+` operand included), in a module that lists or reads files; a template or concatenation that could expand to an encoded record's path, in any module; a scanner still in `unwiredLegalRecordScanners`; a `legalRecordLabel(...)` call outside rule e's places; a literal holding a label that is read in the same expression; an `expect(label)` chain using a matcher off the list. Outside it, by decision and not a defect: a name or path computed at run time (a name read from data, a path built from variables whose own text holds no part of the directory, such as `join(dir, name)` with `dir` from another module); a label stored in an object or array held by a variable and read back later, in the same module or another (the guard test keeps this as a documented limit that passes); readers that are not JS or TS; and the exempt modules (`legalRecordGuardExemptions`: the loader, its test, the codec, the migration proof, its test, the guard and its test). Two other checks catch that second case's consequence: a bare parse of an encoded file gives the wrapper without `candidates`, which strict readers refuse, and L2 and L4 require `mvp:status` and the inventory check unchanged. A coarser rule (no file read in a module that uses a label) can close it when L3 rewrites the Spells tests (queue: `legal-guard-coarse-label`). Today no Python or shell script parses a legal record: `agent_launch_guard.py` excludes the directory from its scan and `prep-lib.sh` only tests that a batch's file exists.

The codec's contract is narrow, not total over JSON: `encodeLegalRecord` refuses by name a record with the encoded form's top-level key `encoding: "legal-record-v1"`, and a single-key `$text` or `$entry` object anywhere in it (`legalRecordEncodingRefusal`; no committed record has either). A file is the encoded form only when it is the whole wrapper (exactly `encoding`, `entries`, `texts` and `value`, each of its type, in any order or layout), so dual read returns any other record as given, and check 2 (`findLegalRecordProblems`, `catalog:format --check`) finds an encoded file by that parsed structure, however an editor reorders or reformats it. Ids are content hashes, a text's of its JSON form so lone surrogates stay distinct; encoding refuses two contents that share an id.

## Armor, shield and natural armor bonuses

Armor, shield and natural armor bonuses each have their own AC leaf: `ac.armor`, `ac.shield` and `ac.natural`. A Modifier on `ac` goes to the leaf its bonus type names, and an equipped armor or shield adds its bonus to its own leaf. Bonuses of the same type don't stack (CRB p. 12), but AC adds its leaves together without comparing bonus types across them. So one of these bonuses on `ac.other` stacks with a real armor, shield or natural armor bonus: Cooperative Swarmer's +2 shield bonus on `ac.other` beside a light steel shield (+1) adds 3 to AC instead of 2. Curate these bonuses on `ac` or on their own leaf.

[`tests/catalog/ac-other-defense-bonuses.test.ts`](../../tests/catalog/ac-other-defense-bonuses.test.ts) scans every curated record's Modifiers and fails on an armor, shield or natural armor bonus on `ac.other`, apart from the held violations #734 retargets before their holds clear: Swordplay Deflection, Shield Gauntlet Style, Improvised Defenses, Cornugon Shield (two Modifiers) and Cooperative Swarmer. ## Reviewed change replacements

The overlay appends outputs; it can't replace or drop an upstream change. When the published rule contradicts a raw change's formula, a row in [`reviewed-change-replacements.ts`](../../scripts/catalog/reviewed-change-replacements.ts) replaces that formula for one record. The row names the pinned record, its exact raw change (target, formula and type), the replacement formula, an optional condition (`unarmored`, or `armorAtMost` `medium`, `light` or, since rotation-5, `none`), the evidence, and its review state: written `drafted`, with no reviewer, it applies nothing; once the curation review approves exactly that row, root marks it `checked` with the reviewer and date (stats-d2). ## Reviewed unsupported changes

A row in `reviewedUnsupportedChanges` ([`racial-trait-rules.ts`](../../scripts/catalog/racial-trait-rules.ts)) withholds one raw change: the importer reports it under `unsupported` with the row's reason and maps nothing, so the change contributes nothing to any total. It is for a change the source gives only in a situation no Modifier condition states, or one another reviewed output already supplies. The row names the pinned record, its exact raw change (target, formula and type) and the reason, citing the text it rests on (PRD line, pinned body, PCGen line). The [importer README](README.md) lists the rows.

**Who reviews a row and how it is approved.** The same rule as a replacement row: the curation review confirms exactly that row against the text it cites, and root records it. A row has no review state in the code (unlike a replacement's `drafted` or `checked`): it applies as soon as it is committed, so it lands only in a slice whose curation review confirmed it, and root names that review in the slice's record. Withholding can't add a bonus; what the review checks is that the cited condition is real and that no condition the sheet has states it exactly (a condition the grammar expresses exactly is a replacement row instead).

**A stale row fails the import** (stats-d2 fix r2). Before, a row whose upstream change moved stopped matching silently, and the change mapped as an unconditional Modifier. Now a row that matches no raw change of the record it names fails `mapEntry` and the import, naming each such row and what the record carries instead: "The reviewed unsupported change no longer matches its record: pf1/3MKN05JEqEYrNx7Q has no raw change landSpeed 10 (base); its landSpeed changes are 20 (base)." That covers a changed formula, target or type and a removed change in any input. A removed record, or a typo in a row's record key, fails every caller that reads verified checkouts at the pins, through the same `wholeCorpus` option the rule-value records use (fix r3: before, the stale-row check had its own option, `verifiedCheckouts`, which fix r2 added and fix r3 folded into `wholeCorpus` because the two meant the same thing; reports of fix r2 and round 3 name it. ## Reviewed description corrections

The overlay appends outputs and the description record binds the whole raw body, so neither can change what an entry's description says. When an owner decision corrects a stated value in the text, a row in [`reviewed-description-corrections.ts`](../../scripts/catalog/reviewed-description-corrections.ts) replaces one exact span of plain text in one record's raw description. The row names the pinned record's upstream key (`<repo>/<_id>`), the SHA-256 of its raw description body (`sourceBody`), the exact span (`from`) and its replacement (`to`), the evidence, and the reviewer and date.

- **Plain text only.** A correction changes text, never markup. The rule is an allow-list, not a list of markup syntaxes:
  - `from` and `to` contain none of `<`, `>`, `&`, `@`, `[`, `]`, `{`, `}`, `"`, `'`, backslash, or a line break. The module refuses such a row when it loads.
  - The span lies inside one text node of the body, parsed by the sanitizer's parser (parse5). That node's raw source must be exactly its text and contain none of those characters either.
  - So a span can't reach into a tag, attribute, entity or comment. It can't sit inside a text node that holds a `@UUID[…]{…}` link or a `[[…]]` inline roll. Nor can it assemble one from neighbouring text.
  - **What users see.** Comments and stripped or kept elements can split a roll or link around a plain node, as in `[[<!---->2d8*3<!---->]]`. So applying also checks the real sanitizer's output (`sanitizeDescription`) for the original and the corrected body:
    - Each span occurs exactly once in the sanitized original, outside every tag.
    - The text run around the span, between the nearest tags of the sanitized output, holds none of `[ ] { } @`.
    - The span intersects no construct (target, options or label) that the real grammar finds in the sanitized HTML or its visible text. The grammar is `constructGrammar`, copied verbatim from the code that reads descriptions, never hand-written. A test compares its PF1 patterns, pattern for pattern, with the pinned PF1 v11.11 source (`tests/fixtures/pinned/pf1/module/chat/text-enrichers.mjs` and `module/utils/lib.mjs`):
      - every PF1 v11.11 text enricher: `@Apply`, `@Toggle`, `@Save`, `@Ability`, `@Skill`, `@Use`, `@Action`, `@Heal`/`@Damage`, `@Browse`, `@Weight`, `@Distance`, `@Condition`, `@Draw` and `@Source`;
      - the PF1 and Foundry inline roll `[[…]]`;
      - the importer's own link and roll patterns;
      - Foundry's `@<Type>[target]{label}` document links, for any type name.
    - The sanitized correction equals the sanitized original with exactly those substitutions and nothing else, and the grammar's constructs (kind, text and order) are identical before and after.
  - Together, no catalog link or closure edge can appear, vanish or change, and no roll can change. Only the entry's own content fingerprint moves.
  - A value inside a table cell is corrected by its plain text: `100 lbs.` → `110 lbs.`, not the whole `<td>…</td>`.
- **Applying.** `mapEntry` applies a record's rows to its raw body, then sanitizes the result as the entry's `description`. A row applies only when the body's hash equals its `descriptionSha256`, its span occurs exactly once, and it passes the plain-text rule. Rows of one record apply together, against the original text.
- **Refused rows.** When any row of a record fails a check, none of that record's rows applies. The entry gets one `description.correction` unsupported issue per row. A refused row's issue says which check failed: the description changed since review, the span or replacement is not plain text, the span is missing or repeated, the span is not inside one plain text node, the spans overlap, or a sanitized-output check failed (the span isn't exactly once there, it's inside a tag, its text run holds `[ ] { } @`, it's inside an enricher, link or inline roll, or the sanitized result or its constructs change beyond the spans). The record's other rows report that they were not applied. A raw-text change already moves the record's content binding, so its assessment reopens anyway.
- **Loading.** The module also refuses, when it loads, a row with an empty or malformed field, and two rows of one record with the same span or spans that could overlap.
- **Derived texts stay raw.** Only the entry's own `description` changes. The description curation record (`collectDescriptionInputs`), the race description re-homes, the race ability-trait line and the inventory `descriptionSha256` keep reading and hashing the raw record.
- **Re-binding.** A row changes the entry's content, so adding one re-binds the record's Attribution Assessment and every assessment whose content covers the entry, lists them, and goes through the admission review, as for a change replacement.

The table holds four rows: the Elf and Half-Elf male base weights, corrected to PCGen's Core Essentials biosettings under the owner's 2026-11-01 decision (#328 Step B, [races-328.md](races-328.md#step-b-elf-and-half-elf-male-base-weight)). [`reviewed-description-corrections.test.ts`](../../tests/catalog/reviewed-description-corrections.test.ts) checks every rule with test-only rows on the pinned Elf and Half-Elf, sweeps every pinned pf1 and pf1-content description to show that every span touching markup is refused, and that every run inside a grammar construct is refused when comments split it into its own text node (by the text-run check) or a kept tag does (by the grammar). It checks that each production row applies cleanly to its pinned record, that the Step B rows equal PCGen's base weight and the range base + 2…16 × multiplier, and that the copied grammar equals the pinned PF1 source. The table isn't registered for automatic row merges between parallel batches (`table-merge.ts`, `prep_table_files`): its rows are built through `parseDescriptionCorrections` with shared fields, which the merge's literal-row parser can't split, so two batches that both add rows need a hand merge.

## Notice holds from content batches

A batch that cannot accept a notice records the hold in its legal evidence file under `scripts/catalog/legal/`, in one of two shapes: a `holds[]` entry with `id` and the held Registry `noticeKey` (notice-review batches such as #264/#265), or a `noticeRequirements[]` entry with a non-null `holdId`, whose `book` and `registryKeys` are held (content batches such as #328–#330). Several batches may name the same hold ID.

Two more evidence fields name held notices:

- `relatedNoticeKeys` on a `holds[]` entry lists further Registry keys the same hold covers, such as the other line of a variant comparison (#285). They are held notices of that hold, like its `noticeKey`.
- `previouslyReviewedIn` names the evidence file of an earlier batch that already reviewed a notice, so the later batch records no new hold for it. On an `inventoryOccurrences[]` entry it is one path or `null` (#271); on a `noticeRequirements[]` entry it is a list of paths (#523). Each named file must record an enforced hold on that notice. A requirement without a `holdId` must instead appear without a hold in each named file.

The admission gate enforces these holds through [`scripts/catalog/legal/held-notices.json`](../../scripts/catalog/legal/held-notices.json): one entry per hold ID with every held notice code and the evidence files that record it. Add each new batch hold there in the same change as its evidence; `tests/catalog/notice-holds.test.ts` scans every evidence file in that directory and fails on a recorded hold that is missing or narrower in `held-notices.json`, on an entry no evidence records, or on a `previouslyReviewedIn` notice that the named file does not hold. A trailing-space variant of a reviewed line therefore has no Registry record or alias of its own (#267–#272). `tests/catalog/section15-registry.test.ts` checks every notice.

A candidate whose required notices include a held code, or any identifier of the Registry notice a held code names, is held with the reason `Notice holds: <code> (<hold IDs>).` even when its assessment, evidence and notice bindings are otherwise current; a reviewed Registry status does not lift the hold. Content-level holds (`holdIds` naming whole-content comparisons) stay expressed through `unresolved` Attribution Assessments, which the [#227 rule](#the-227-admission-rule) now overrides for a declared book, and the importer's source-matched groups stay in `known-notice-holds.json`.

## Notice dependencies

A candidate whose rules depend on another book must list that book's notice in `requiredNotices`. `pnpm catalog:notice-deps` checks every curated candidate (one with `requiredNotices`) in the batch inventories under `scripts/catalog/legal/` against the inherited-rule dependencies the inventory itself records: `inheritedRuleNotices`, `fullContentReview.inheritedRules` and `inheritedNoticeReview` books; the cited sources of `inheritedRuleSourceEvidence` and `mechanicsReview.inheritedRuleEvidence` records (any one of a record's books suffices, so the rule can miss a gap but never fails falsely); and the notices of each `noticeHoldIds` hold. Each dependency's notice must be required, matched by code or Registry identifier, and be a reviewed Registry notice or held in `held-notices.json`. Prose is never read for this rule. Linked records are not dependencies, since links include prerequisite feats: a `linkedContentReview` record whose books are not required prints a warning, and links to records in other inventories are not checked. `tests/catalog/notice-dependencies.test.ts` runs the same check over the committed inventories.

A gap fails unless [`notice-dependency-waivers.json`](../../scripts/catalog/legal/notice-dependency-waivers.json) waives that candidate key and notice with a reason, reviewer and date. A waiver that no longer matches a gap fails as stale; remove it in the change that fixes the inventory. Record dependencies in these fields when curating; a dependency left only in prose is not checked.

The command also prints warnings, never failures, when a candidate's reviewed description names a term from the reviewed table in [`notice-dependencies.ts`](../../scripts/catalog/notice-dependencies.ts) without that book's notice: stamina (PZO1131), Story feat or Completion Benefit (PZO1125), mythic (PZO1126), advanced simple template (PZO1112), mascot (PZO9454), Wolf Style (PZO9439) and Linnorm Style (PZO9470). Each term cites the review finding it comes from (#337, #339, #341, #520 and #522). Check each warning against the text; record a real dependency, or leave a false positive as it is.

## Parallel batches

Two or three curation batches can run in parallel worktrees and land one at a time. Every batch edits five shared files: the Curation Overlay [`reviewed-curation.json`](../../scripts/catalog/reviewed-curation.json), [`attribution-assessments.json`](../../src/lib/catalog/data/attribution-assessments.json), [`attribution-evidence.json`](../../src/lib/catalog/data/attribution-evidence.json), the Section 15 Registry [`section15-registry.json`](../../src/lib/catalog/data/section15-registry.json) and [`held-notices.json`](../../scripts/catalog/legal/held-notices.json). Each file has one canonical form, written by [`scripts/catalog/data-files.ts`](../../scripts/catalog/data-files.ts), so a batch changes only the lines of its own entries:

- Top-level entries are sorted by stable identity: overlay records by exact binding (`externalKey`, kind, target, action and conditional IDs, text hash), structure records by `externalKey`, field set and `sourceSha256`, shared Situations by `key`, assessments by `externalKey`, evidence by ID, Registry notices by code and notice holds by `id`. Readers look entries up by identity, so this order carries no meaning. The drafter matches wording to the first Situation with that alias, so two Situations may not share an alias.
- Fields follow schema order; identity-keyed maps, such as an assessment's `evidenceFingerprints`, are sorted. Nested arrays (outputs, diagnostics, aliases, provenance, required notices, a hold's notices) keep their authored order. A structure record's `fields` are sorted by field, and an empty `structures` collection is left out.
- Two-space indentation and a trailing newline. The overlay escapes every non-ASCII character as `\uXXXX`; the other files keep UTF-8 text.
- The evidence file stores repeated evidence once (#744). Its root holds `evidence`, each entry by ID, and `shared`, blobs named by the first 24 hex characters of the SHA-256 of their text. Every JSON value of 512 bytes or more inside an entry's content is a blob, and blobs nest. An entry keeps its text either as literal `content` (prose, or JSON with nothing that large) or as `parts`: literal text and `{ "ref": … }` blob references, one per line, which join to exactly the reviewed content. Each entry's encoding depends only on its own content. Every reader, the admission gate and every fingerprint see the decoded `{ content, revoked?, conclusion? }` entries, through [`attribution-evidence-codec.ts`](../../src/lib/catalog/attribution-evidence-codec.ts), which refuses a missing, mismatched, cyclic or unused blob.

The drafter writes `records.json` in this form. After copying reviewed records into the overlay, or editing any of these files by hand, run `pnpm catalog:format`. Write a new or changed evidence entry with plain `content`; `pnpm catalog:format` encodes it and drops blobs no entry uses any more. It also accepts the earlier plain-map evidence file. `pnpm catalog:format --check` writes nothing and fails on any non-canonical file, including evidence still in the plain form, an unencoded large value or an unused blob, and on a missing or mismatched blob or an evidence ID or blob named twice; `tests/catalog/data-files.test.ts` runs the same check.

To land a batch after another has merged:

1. Rebase the batch branch onto the updated base: `git rebase <base>`.
2. When any of the five files or the two tables below conflicts, run `pnpm catalog:merge`. It reads Git's base, ours and theirs versions of each conflicted data file and merges them by identity: entries added on either side are kept, and a change or deletion made on one side wins. During a rebase, “ours” is the base branch and “theirs” is the batch commit being replayed. The merged file is validated and written in canonical form. Evidence merges by decoded entry, refuses an evidence ID named twice on any side, and accepts the earlier plain-map form on any side, so a branch from before #744 rebases the same way; the merged file keeps only the blobs its entries use. It merges the two TypeScript tables batches append rows to the same way, row by row: `reviewedChangeReplacements` in `scripts/catalog/reviewed-change-replacements.ts` (a row is identified by `externalKey` and `change`) and `danglingCatalogLinks` in `tests/catalog/cross-batch-bindings.ts` (by `uuid`). The result keeps the base's rows, then the rows ours added, then those theirs added, takes a row changed on one side only, and is formatted with Prettier. Resolve other conflicted files as usual.
3. `pnpm catalog:merge` refuses, and leaves that file untouched, when both sides changed the same identity differently (for example two different definitions of one shared Situation, Registry notice, notice hold or assessment), when one side deleted an entry the other changed, when two Situations claim one alias, when two Registry notices newly claim one identifier, or when the merged file fails its schema (such as a record naming a Situation the other side removed). For a table it also refuses a row removed or reordered on either side, a row both sides changed or added differently, and any change outside the table literal. Its report names each identity and the differing fields. Decide the correct content with both batches' reviews, edit the file, then run `pnpm catalog:format`.
4. `git add` the resolved files, then `git rebase --continue`.
5. Run `pnpm catalog:format --check`, then re-run the batch's gates: its tests, `pnpm test tests/catalog`, and the curation previews and admission runs its ticket documents. A merge of data files does not re-review content; a rebase that changes another batch's evidence or Registry entries can reopen assessments, which the gates report.

Explicit versions can also be merged into a file: `pnpm catalog:merge scripts/catalog/reviewed-curation.json --base base.json --ours ours.json --theirs theirs.json`. Without `--base`, the merge is a plain union by identity; a table needs `--base`.

`cur-prep.sh` and `land-queue.sh` (`scripts/orchestration/`) run `pnpm catalog:merge` when a rebase stops on these files only (`prep_merge_re` in `prep-lib.sh`); a conflict it leaves unresolved, or in any other file, stops them for a hand resolution.

Generated launch artifacts are never merged, by Git or by hand. `cur-prep.sh` resolves a rebase that conflicts in any of the regeneration bundle (`prep_regen_conflicts` in `prep-lib.sh`, every one of `prep_regen_files`), and in the data files besides:

- the overview `docs/catalog-import/campaign-mvp-inventory.md`;
- `scripts/catalog/scopes/campaign-mvp-v1.json`, `campaign-mvp-v1.authority.json`, `campaign-mvp-v1.notices.json`, `campaign-mvp-v1.records.json` and `campaign-mvp-v1.verification.json`;
- the authored scope documents `campaign-mvp-v1.advanced.json`, `checkpoints.json`, `companions.json` and `core.json`, whose batch changes the check in step 2 refuses;
- the #227 scripted match `scripts/catalog/legal/attribution-227-matches.json` and the party scope `scripts/catalog/scopes/campaign-party-v1.json`;
- the CLI pin in `tests/catalog/launch-document.test.ts`.

Until gate-slim-a (2026-11-11) prep resolved only five of these, and a conflict in the notice authority stopped the CL8 prep on 2026-11-10, although prep regenerates it. Until prep-regen-chain (2026-11-17) prep's chain lacked the legal authority, the scripted match and the party scope, so a notice batch rebased over another was refused on its Registry binding and regenerated by hand.

It regenerates them instead (`prep_regenerate`, `scripts/orchestration/prep-regen.ts`):

1. **Set aside.** At each stop, it marks the conflicted artifacts and finishes that rebase step.
2. **Check the batch.** After the rebase, `prep-regen.ts check` refuses a batch whose own change regeneration from the merged inputs would not reproduce, naming the file. Content the chain does not write is the batch's own and would be lost; a fact the chain writes is reproduced, as long as it follows from the batch's inputs:
   - content in an authored scope document: `advanced`, `checkpoints`, `companions` or `core`, or the authority beyond the two facts the legal authority rebinds, its notice-authority hash and the hashes of its `resource/section15-registry` binding;
   - a Registry binding the batch moved to a hash its own `section15-registry.json` does not have (one it left is rebound from the merged Registry);
   - a change to the launch-document test other than its pinned values and comment lines added just above them.

   `tests/prep-regen.test.ts` covers each case; `cur-prep.test.sh` runs the real check in prep on a notice batch rebased over another, which passes, and on one whose binding does not follow from its Registry, which stops prep.

   Then `prep_regen_reproduce` (`prep-lib.sh`) does to the batch's own commit what steps 3 and 4 do to the rebased one. In a scratch clone of the batch's commit before the rebase, it takes the side of the commit the batch was made on for every path in `prep_regen_files`, and runs the chain from the batch's own inputs with the batch's own generators. Every path the batch changed must come out as the batch committed it, or prep refuses, naming the paths: a generated artifact edited by hand (the scripted match or the party scope too, which the check above does not read) or authored content the chain does not write comes out as the commit the batch was made on had it. A path the batch left is never refused, since nothing of the batch's is dropped there. This covers the whole bundle by construction, so a path added to `prep_regen_files` is covered too; `cur-prep.test.sh` hand-edits each path in turn and expects a refusal. It costs one more run of the chain before the merged one (2026-11-18, on the incident's notice batch `39600ca5`, which it reproduced on all eight paths that batch changed: 929 s, the clone and its offline install a few seconds of it; 2.4 GiB real at its peak, the chain's own, so a regenerating prep takes about twice as long at the same peak).

3. **Take the base side.** The scope documents share one records dictionary, so it takes the base side of the whole regeneration bundle (`prep_regen_files`), conflicted or not.
4. **Regenerate** from the merged inputs, by the regeneration chain (`prep_regen_steps` in `prep-lib.sh`, its one step list), in order:
   1. `pnpm -s catalog:launch-legal-authority --write`: the notice authority, its hash and the authority's Registry binding, from a fresh pinned build;
   2. `pnpm -s catalog:attribution-227-matches --write`: the #227 scripted match;
   3. `pnpm -s catalog:launch-inventory --write`: the inventory, re-compacting the scope documents;
   4. `pnpm -s catalog:party-scope --write`: the party scope;
   5. `pnpm -s catalog:launch-inventory --verify --write`: the verification projection, which binds the scripted match;
   6. the pin (`prep-regen.ts pin`): the base side's test, with the batch's added comment lines, pinning the summary that step 3 printed.

   Curators regenerating by hand run the same steps in the same order, each its own capped command with no `CAPPED_KIND`: `capped.sh` reserves `curator-inventory` (3.5 GiB) for each by its words, the party scope included, whose largest recorded real peak, 1.77 GiB over 162 runs (`admission/peaks.log` to 2026-11-18), is above `curator-light`'s 1.5 GiB seed, so a light override would under-reserve it and raise the small scripts' class ([operations.md](../agents/orchestration/operations.md), measured small commands); prep runs the steps inside its own reservation and reserves no class per step; a change to `pcgen-notice-books.json` may first need `section15-match.ts`, whose output is a reviewed input, not a generated artifact. `cur-prep.test.sh` checks that prep runs `prep_regen_steps` in order and that this list is that list. The chain adds about 6.5 minutes to a prep that regenerates (2026-11-17: the scripted match and the party scope about 3 minutes each, the legal authority's build in place of the earlier notice step); its largest step is still `--verify --write`.

5. **Amend and record.** It amends the prep commit. The prep log says which artifacts conflicted, and so does the receipt's `regenerated=` field (`-` when nothing was regenerated), which names the chain.
6. **Check as usual.** Prep then runs its normal checks, `catalog:launch-inventory --check` and `--verify --check` among them, and `catalog:attribution-227-matches --check`: the scripted match authorizes admission, so a fresh generation must equal the committed file wherever it is relied on (cavalier-master-tactician fix r4); `code-rebase.sh` runs the same check at the end of its chain, and the landing suite holds the committed file to a fresh generation too (`attribution-227-matches-fresh.test.ts`, a gate-host audit in `scripts/orchestration/host-audits.json`: CI lacks the pinned checkouts and skips it; `attribution-227-generation.ts` is the generation the command and the test share).

Prep stops with exit 2, leaving the rebase in progress, on a conflict in any other path. It also stops on a refused batch change or a failed generator, leaving the rebased commit unamended.

Prep's message for a generated artifact never asks for a hand resolution. It says the artifacts are never hand-merged, and asks the operator to repair the inputs or the generator and regenerate them from the merged inputs (the regeneration chain, which it names), or to escalate. `scripts/orchestration/cur-prep.test.sh` tests each of these cases, including a conflict in the notice authority and in each of the bundle's other paths, each regenerated, and `tests/prep-regen.test.ts` tests the batch check and the pin. Curation items in `land-queue.sh` go through `cur-prep.sh`, so this covers them; the rebase it runs for an `impl/` item still stops on these artifacts.

## Preservation checks

A batch's tests check what the batch owns, not the rest of the repository. Owner decision of 2026-10-13 (#749), generalising the curation amendment of 2026-10-12:

- **Own rows, as recorded.** Each batch's description records, Attribution Assessments, evidence entries and holds stay as its inventory (`scripts/catalog/legal/<batch>.json`) recorded them: the checked description and its text hash (for an Item Ability, its checked `itemAbility` record, which binds the same description, since the prose pass skips Item Abilities: #501), the assessment's status, required notices, evidence ID, content and mapping fingerprints and whole-content hold, the evidence entry's fingerprint and source hash, and its notice holds with their notices. The evidence fingerprint comes from the inventory's binding snapshot; #343 and #345 to #347 recorded none, so [`recorded-evidence-baselines.json`](../../tests/catalog/recorded-evidence-baselines.json) keeps the evidence hashes that the next batch's historical manifest committed for them, derived once and checked against the data at the time. [`tests/catalog/batch-ownership.ts`](../../tests/catalog/batch-ownership.ts) implements these checks for the earlier batches; [`batch-ownership.test.ts`](../../tests/catalog/batch-ownership.test.ts) shows each one fails when such a row is altered or removed.
- **Shared files by entry.** The Registry, notice reviews, held notices, the Curation Overlay, assessments, evidence and the legal README are checked only for the batch's own entries, never byte for byte and never for other batches' rows. A Registry notice the batch's review cited must keep its key (and a hash key must still name the text the review hashed); its current text is checked only through the batch's assessment bindings.
- **Bindings against current data.** An assessment's notice fingerprints must match the current Registry, and a recorded binding snapshot must match the current binding's content, mapping and evidence fingerprints. A reviewed notice correction, whether a new record or an in-place edit, keeps earlier batches passing once it re-binds the assessments that require the notice.
- **Release fixtures against their own identity.** A committed release fixture is checked against the calculation identity it recorded, which must be one the identities module has known (current, prior or superseded), not against the current one. [Rotating the calculation identities](releases.md#rotate-the-calculation-identities) therefore leaves earlier batches passing.
- **No infrastructure freezes.** Tests do not hash `package.json`, the lockfile, Vitest or ESLint configuration, scripts, skills, brief templates, other batches' inventories or fixtures, or the repository's file list.

Earlier batches' whole-history manifests that no test reads are removed (#744 snapshot cleanup): every `original-identities.json` and `local-binding-proof.json`, the `preserved.json` of #530 to #536 and the `protected-context.json` of #355 and #534 to #536; git history keeps their content. The rest stay because a test still reads them: #528's and #529's `preserved.json`, whose keys must keep empty description outputs and diagnostics, and the `protected-context.json` of #350 to #354 and #530 to #533, whose roots, closures and definition fingerprints their own tests and #352's and #353's compare with current data. `historical-binding-proof.json` and `verification.json` stay as recorded until the rest of #744. New batches add no such manifests: keep the shared files' diff to the batch's own keys and rely on `pnpm test tests/catalog`, `catalog:pin`, `catalog:notice-deps` and `catalog:format --check`.

Upstream files come from the pinned store ([`tests/fixtures/pinned/README.md`](../../tests/fixtures/pinned/README.md)): read them with its loaders, or add a missing one there, never as a copy in the batch folder. Earlier batches' copies are relative links into the store (`pnpm catalog:link-copies`), all but the one bound copy the README names, and `tests/catalog/pinned-copies.test.ts` fails on any fixture file identical to a pinned one. A test that copies such a folder passes `dereference: true` to `cp`, and a run that writes into the store fails (the README's "Earlier batches' links").

### Protected and governing records

Batches before #749 kept some records' Notes empty so earlier batches' frozen bindings wouldn't change: protected roots, keys that appear in earlier batches' fixtures, and bodies that govern another entry. Since #749 the checks compare bindings with current data, so a batch completes such a record's Note from the evidence instead. A Note changes the entry's content fingerprint, so the curator lists, in the batch report, every content binding and dependent Attribution Assessment it changes: the entry's own, and each entry whose binding covers it as a governing or linked body, with its batch and the inventory and test that record it. The change re-binds each of them, and the curation review checks every listed one and that the list is complete. Filling the Notes earlier batches left empty, and the rest of the historical artifact cleanup, stay under #744.

### Cross-batch content bindings (#756)

An assessment's content fingerprint hashes every whole entry in its full-corpus content closure, curated Modifiers and Notes included. So when a batch curates an entry inside an earlier batch's closure (a linked body, a shared target, a related variant), the earlier assessment goes stale. The earlier batch's tests re-bind against its own fixture copy of that entry, so they keep passing. #370 found three such cases with #369 and #371.

**Rule:** the later-landing batch re-binds every earlier assessment whose closure it changes. It updates the earlier batch's fixture copy of the changed entry, re-binds the assessment with `buildAssessmentBinding` over a full `catalog:preview`, and updates that batch's inventory `currentBinding`. It changes no disposition, evidence, notice or hold, and lists each re-bound assessment in its report, as for [protected and governing records](#protected-and-governing-records).

**Check:** [`cross-batch-bindings.test.ts`](../../tests/catalog/cross-batch-bindings.test.ts) enforces the rule in prep and in the landing gate. It reads only committed fixtures (a few seconds, no preview run).

- **Staleness.** For every batch fixture (`preview.json`, `binding-preview.json`, and the registered #738 full-context supplement), the check compares each copy of an entry another batch owns with that batch's own fixture entry. That batch's tests check its fixture entry against a fresh import. It compares whole entries, every curation-derived field included: Modifiers, Notes, `detail`, `sourceKey` and the `unsupported` diagnostics. It normalizes only two proven import-scope differences:
  - A bounded import strips description links to entries outside its selection and reports each one as `description.link`.
  - A race lists only the Racial Traits its import included and keeps the mechanics of the rest (#719), so a race whose list is a strict subset of the other copy's is skipped. Curation never changes that list. An alternate trait's `replaces`, which #721 resolves through curation, is compared.

  Where a copy differs, the check re-binds the fixture batch's assessments with the owner's entry in place and fails on every binding that changes. The failure names the assessment, its recorded fingerprint, and the batch and entry that changed. Accepted stale bindings are pinned with their recorded and current fingerprints, so further drift fails too.

- **Coverage.** Every assessed record's closure must be committed in its batch's fixtures. A fixture file holds a closure when every key the closure reaches is in it, and no entry in the closure had a link to a catalog entry stripped. A bounded import strips links to entries outside its selection, so each stripped link into a pack the importer maps is a dependency the file lacks. Links into excluded or unassigned packs never resolve. One link into a mapped pack names a record the pinned sources lack, and is listed in the test. The check fails on any batch with an assessment whose closure no fixture file holds, or with no fixture entry at all. A new batch therefore commits its full-corpus closures, as the traits batches do in `preview.json` (`closure`) and #355 and #520 to #536 do in `binding-preview.json`. Batches with no links outside themselves, such as feats #334 to #366, need no copies.

The #738 supplement is registered with each owning batch for its 99 roots. Its entries never supply owner truth: both roots and dependencies are compared against the ordinary owner fixtures, including roots owned by the same batch. Its complete closures also participate in coverage checks; the historical bounded extraction assertions still replay separately.

The full-corpus re-bind stays the authority. The check's re-bound fingerprint can differ from it where the copy's own import scope does.

### Test memory

Each Vitest process gets an explicit V8 heap instead of the size Node derives from the cgroup: 2,096 MB under the curator caps (12G hard, 8G soft), which #536's test outgrew at #544, and 4,144 MB under the gate caps (15G, no soft limit: the smallest cap that keeps it; 14.5G and below give 2,096 MB; [gate memory](../agents/orchestration/operations.md#gate-memory)). The `test` and `test:watch` scripts give the parent 4,096 MB on its own `node` command line: it holds the module graph, and #538 was a parent OOM. Each worker, and every CLI a test spawns, gets 3,072 MB through `NODE_OPTIONS` (#744): Vitest passes its forks the environment but not the parent's flags, and a spawned CLI inherits the worker's environment. `tests/test-heap-limits.test.ts` checks the worker and CLI limit. `scripts/orchestration/triage-failures.sh` still exports 4,096 MB for its single-test retries, which run outside the scripts. A heap flag bounds one process, not the sum: at two workers that is 4 + 2 × 3 GB of ceilings, plus the CLIs the workers spawn and their esbuild, which no flag caps.

The CLI default paths (`catalog:preview`, `catalog:release` without `--attribution` and `catalog:conditions`) read the committed notice register and frozen stored notices only (`register-admission.ts`, pbl-register-only), never the 93 MB evidence JSON; before that they read the committed attribution files as files and decoded them, instead of having tsx and esbuild compile the evidence into a module.
