# Local validation and gate operation

New operations use repository tooling. Active external frozen bundles, old failed inputs/helpers/reports and authentic review/admission evidence remain immutable history; changing repository scripts does not qualify them or amend a frozen operation, and the parent owns adoption and live-state migration after review and qualification. Exact rules of the optional gate modes: [gate modes](../orchestration-reference/gate-modes.md). The complete validation and operator contracts, verbatim: [full contracts](../orchestration-reference/gate-operator-internals.md).

## Validation evidence

Before coding, select one impact-based plan, naming why each check is necessary and the configuration/runtime inputs it reads. Package scripts are authoritative for commands and heaps: `pnpm -s typecheck`, `pnpm -s lint` (including its 8192-MB old-space and 256-MB semi-space ESLint options), `pnpm test <paths>`, writer/artifact checks, and local codegen/browser checks when affected. Orchestration shell tests may be selected by their exact `scripts/orchestration/*.test.sh` entry path; the recorder executes no shell expressions or callback strings. The full queue stays mandatory, and shared-code regressions block outside a selected content slice.

Store a JSON plan in the external task directory:

```json
{
  "version": 1,
  "main": "/absolute/main",
  "orch": "/absolute/shared/ep-orch",
  "worktree": "/absolute/app-owned/worktree",
  "base": "FULL_BASE_SHA",
  "fullQueueRequired": true,
  "checks": {
    "types": {
      "impact": "Changed public types and their consumers",
      "argv": ["pnpm", "-s", "typecheck"],
      "inputs": ["tsconfig.json", "convex/tsconfig.json"]
    },
    "lint": {
      "impact": "Changed code must satisfy repository lint and unused checks",
      "argv": ["pnpm", "-s", "lint"],
      "inputs": ["eslint.config.mjs", "knip.jsonc"]
    }
  }
}
```

Resolve the actual configuration paths in this checkout, and include backend image/configuration or browser runtime input files when relevant; private environment files stay out of inputs. Run the recorder bare, with exactly `BOUNDED_WORKERS=2 BOUNDED_CPU=600% LC_ALL=C.UTF-8` exported; it caps its own child through `capped.sh`. Record and verify serially:

```bash
export BOUNDED_WORKERS=2 BOUNDED_CPU=600% LC_ALL=C.UTF-8
python3 -B scripts/orchestration/validation.py run /absolute/plan.json types /absolute/ep-orch/run/types-attempt-1
python3 -B scripts/orchestration/validation.py verify /absolute/plan.json types /absolute/ep-orch/run/types-attempt-1/receipt.json
```

The recorder and the full reuse boundary reject every `CAPPED_*` and `ADMISSION_*` override and every `BOUNDED_*` override except the canonical two (or their unset defaults); leave `CAPPED_KIND` unset so the wrapper classifies the planned command. Current receipts bind the canonical effective wrapper-control contract: receipts recorded under the earlier 1-worker / 400% contract, or missing that contract, need fresh recording for reuse and remain historical evidence. Each result directory is create-only, failures included. `verify` names the reason when content, dependencies, configuration, tooling, runtime inputs or environment change; a SHA change alone is not a reason, so a tree-identical squash repeats no author check. A check that is invalidated gets a new evidence directory; keep the failed or obsolete result and cite it with the reason in the report.

Specialized curation prep receipts stay authoritative for light/full catalog preparation, affected older batches, post-rebase counts, branch/path and full-plan escalation; author receipts supplement them. `cur-prep.sh --remote-suite` runs every prep check except Vitest, records the plan and uses admission class `prep-remote`. It writes only its own receipt file, `cur-<n>-prep.remote.receipt` (`tests=remote`), and never `cur-<n>-prep.receipt`, which only a local prep writes; each prep removes both when it starts. A landing under remote checks reads only the remote file and refuses a missing or stale one instead of preparing again. Every other landing reads only the local file, whose Vitest log must be this commit's passing run; otherwise it preps locally. A landing gate runs its complete checks and original suite independently of author-check reuse; only a verified [remote heavy-check manifest](#remote-heavy-checks) replaces its local typecheck, lint and full suite. Full validation contract: [validation evidence](../orchestration-reference/gate-operator-internals.md#validation-evidence).

**Empty validation plans.** A plan with `checks: {}` carries no author receipt into the gate, and `gate.json` `validation.receipts` is then `{}` too: `gate_core.verify_validation` requires the receipt names to equal the plan's check names. The gate still verifies the plan's `{path, sha256}`, `version: 1` and `fullQueueRequired: true`, and that its `main`, `orch`, `worktree` and `base` match the gate's. It verifies no receipt and captures no tool context. An empty plan is correct whenever no author check was recorded with `validation.py`, for example when the author ran its checks through `capped.sh` and reported them. It relaxes nothing, because the landing gate runs its complete checks and original suite either way. A plan that names a check needs that check's original receipt, which is verified at every authorization, so name only checks you recorded.

## Gate operator

`scripts/orchestration/gate-operator.py` owns the single-item prepare/freeze/submit/observe/collect/complete sequence. It runs `land-queue.sh` in a bounded gate unit; the queue owns rebasing, specialized curation prep, full validation and checked `land.sh`. Pairs use the [paired procedure](paired-gates.md); unflagged queue lists stay serial. Root drives it with the [script gate operator](#script-gate-operator); a gate is not a delegated task.

### Script gate operator

Root runs a gate with one command (root, 2026-11-05), from the gate spec `$EP_ORCH/scripts/brief.py ITEM gate ROUND` writes (`R/ITEM-gate-spec-rN.json`):

```bash
BOUNDED_WAIT=1 $EP_ORCH/bounded.sh --detach <label> driver <spec.json>
$S/await.sh <id>
```

- **Sequence:** `gate-run.py` runs what the operator task ran by hand, with the same checks and refusals:
  1. identities, prepared mapping and mode proofs;
  2. the [gate time](#gate-time) fail-fast check: the CI part, known before the gate starts, against the total trigger;
  3. three prelaunch samples 30 s apart at the gate mode's launch guard plus 0.5 GiB and above the disk floor ([gate memory](#gate-memory)), with all five locks free, idle admission and no other heavy unit. Every 10 minutes it prints a blocker line and records it as the probe row's `blocker`: each blocker (locks, admission, heavy units, memory, disk) with its value against its threshold. It stops after 30 minutes when memory is the only blocker or disk is, and after 90 minutes for any other, naming the blockers;
  4. the storage baseline;
  5. `gate-operator.py prepare` and `runtime`;
  6. the stale-admission probe (every 5 s, at most 2 minutes, never killing or removing anything);
  7. a pre-claim check of memory, admission and storage against the baseline;
  8. the retained entry's `resume`, after it writes `gate-time.json` for the queue's total check.
  The observer, collection, `complete`, the frozen runtime and the single submission stay the gate operator's.
- **Inputs:** it writes `gate.json` from the spec with `gate_config.py` and never from prose. It also writes `operator.json`, `control.json`, the empty validation plan, the commit message (the spec's `message`, an optional `message_body` and the trailer; `brief.py` copies both from the item spec, and the commit-tree squash uses that file, so a code gate needs no `--extra` for a body; a curation spec refuses `message_body`, since its prep commit's message file binds the message), `storage-baseline.json`, `environment-precheck.json`, `gate-time-precheck.json` and `gate-time.json`, all create-only in the spec's `inputs_dir`. `preservedEvidence` binds the acceptance, the Q1 records, the driver's own prechecks, the lane check, a curation batch's prep receipt and the spec's `preserve` list. It rebuilds the public environment rather than inheriting it: no `BOUNDED_*`, `CAPPED_*`, `LAND_*` or `VITEST_*` from the unit reaches the gate operator. Unknown spec keys refuse.
- **Operator identity:** `operator.json` is `{kind: "script", path, commit, blob, taskId, runId}`: MAIN's `scripts/orchestration/gate-run.py`, its blob at `BASE` and this run's id. `gate_core.operator_identity` requires that path, `commit` equal to `BASE` and the committed blob. The driver refuses to run when its own bytes are not that blob. Author and reviewer independence, terminal review identity and the exact candidate, base and tree bind as before.
- **Refusals** stop with a recorded reason and launch nothing further: a [gate-time](#gate-time) trigger without root's outside cause, a memory guard, a storage event since the baseline, admission not idle, an identity mismatch (MAIN, WT or driver), a moved base, a prepared-mapping mismatch, a refused mode proof, or a `prepare`/`resume` failure. A stopped gate keeps its attempt and mapping, and its control ends `stopped`.
- **Stop:** `python3 -B $MAIN/scripts/orchestration/gate-run.py --stop <spec.json>` sets the attempt's control to `stopped`. It takes the attempt's publication lock (`publication.lock` in the inputs) that finalization holds while it fixes the verdict and writes the result, so the two never interleave. A stop that wins makes the run report `stopped` (exit 1); after a publication, `--stop` prints `already finished: <verdict>` and changes nothing. Stopping the unit (`systemctl --user stop ep-fresh-<id>`, or SIGTERM/SIGINT) writes the same stopped control at once, whatever the driver is doing. From then on the driver starts no stage and launches no gate-operator command. The gate operator refuses any phase under that control: at submission, observation and completion, with the scoped cancellation and safe collection below. A running command is never killed; the driver waits for it. A stopped run never reports `landed`, even when MAIN reached the candidate before the stop (the result records `mainAtCandidate`). After a stop with a submission claim and no collected result, the driver runs the retained entry's `cancel`.
- **Outputs:** the spec's `result` (`.md`) and the same path as `.json`: the verdict (`landed` or `stopped`), the stop reason, the SHAs, the invocation and receipt, each stage's outcome and exit, and the driver identity. The suite counts cover every suite the gate used: `local` (local and `compare`), `remote` (`compare` and `replace`, from the manifest's report) and `hostAudits` (`replace`; with a host-audits receipt, the receipt's run as the queue verified it, and the source reads `remote+host-audits-receipt`, naming the receipt). Test files are the report's `testResults` entries (`numTotalTestFiles`, `numPassedTestFiles`, `numFailedTestFiles`); Vitest's `numTotalTestSuites`/`numPassedTestSuites` count nested `describe` blocks too and stay labelled suites. A light-lane gate runs no suite.
  - **Gate time** (`gateTime`, and the Markdown's `Gate time` line): the CI part, the host part (with the resume stage's waits it left out, `host.waits`, or `{unavailable}` when they were not recorded), the total, the baseline with its gates and medians (or the gates it could not read, `unreadable`), the percentage against the median total, `totalLowerBound` (the CI part was unreadable), the CI part's check against the total trigger (`ciCheck`) and against its own median (`ciInformation`, information only), the queue's land-check line, root's outside cause and the verdict: `pass`, `refused`, `exempt` or `no baseline` ([gate time](#gate-time)).
  - **Operations** (`ops`, and the Markdown lines after the completion scope): codegen and the E2E preflight (ran, skipped or not run, with the stage log's last line and any preflight retry, from the stage logs the canonical invocation's log names), the canonical unit's real peak (receipt) and kernel `memory.peak` (`$EP_ORCH/bounded/<id>/memory`), load at start (the first prelaunch probe) and end, timeouts (the driver's deadlines, and every one that fired, with the stage it fired in and the time: prelaunch, the post-preparation admission probe, or a 60 s instrumentation command), the terminal lock, admission and heavy-unit state, and the wall time. The end load and terminal state come from the terminal probe, run after every owned command is terminal, which changes nothing: it reads lock holders from `/proc/locks` (`admission.sh held`, which opens, creates and locks no lock file), the ledger with `admission.sh peek` (no mutex, sweep or event; entries no process holds are listed as `stale`, not removed) and `systemctl --user list-units`, plus `/proc/meminfo` and `/proc/loadavg`. A read that fails is unavailable with its reason, never a free lock, an empty ledger or no heavy unit: `held` reports `missing` only when `stat` says the file does not exist and `error` for any other failed read, `peek` exits 3 with nothing on stdout when it cannot read the whole ledger (its directory, an entry that is unreadable or malformed, a lock state, the memory table) or any stage fails: both run under `pipefail`, use only `stat`, `findmnt`, `awk` and `sort` besides bash builtins, check every one of them for its exit and its output, and print only once everything succeeded (`status` formats through the same checked path, so a failed formatter never prints `none` there either), and `idle` is true or false only when every lock, ledger and heavy-unit read succeeded, else unavailable. The driver then keeps it as its own record, `terminal-probe.json`. The prelaunch, reap and preclaim probes keep `admission.sh status`, whose sweep reaps stale reservations. A value without evidence is `{unavailable: <reason>}` and prints as `unavailable (<reason>)`; nothing is filled in. Then the spec's `done_marker`. Exit 0 means landed and completed; 1 means any stop; 2 means an invalid spec or an earlier attempt's files in the way. Nothing is overwritten.
- **Retry after a stop:** the result's `preparedRetry` is the exact `prepared` spec field, `{candidate, mapping, mapping_sha256}`, from the attempt's `mapping.json`. It is null when the attempt stopped before preparation wrote one. `python3 -B $MAIN/scripts/orchestration/gate_config.py retry <prior spec> R/ITEM-gate-spec-rN.json --label <label>` writes the next spec (`brief.py ITEM gate N --label <label> --retry-of <prior spec>` calls it). It keeps the prior spec's BASE, REVIEWED, TREE, branch, archive, reviews, author, acceptance, message and modes, never the squashed HEAD, and renames only the attempt. Its `--extra` takes one key, `gate_time_exempt` (root's outside cause, new or changed after a [gate-time](#gate-time) stop), and the retry spec's notes record it; any other key refuses (`test_a_retry_takes_a_new_or_changed_outside_cause`, `test_a_retry_refuses_every_other_extra_key_and_shape`).
  - With a mapping, the retry is `prepared` mode on the same frame.
  - Without one, it is the prior `prepared` or a fresh squash of the same REVIEWED. A partial preparation that already wrote the archive ref but no mapping refuses that squash ("Archive ref already exists"); root diagnoses it.
  - A moved base allows neither: rebase, prove or re-review, and write a new spec.
- **Retry after an interrupted driver:** a driver that ended without publishing a result (killed, session lost, reboot) is retried by hand: build the next spec from the prior spec plus its `mapping.json` (as for ci-shards r4), and only after checking that no unit of the label (`ep-fresh-<label>-*`, `ep-command-<label>-*`) is live.
- **Detaching:** kind `driver` takes no lock and reserves no memory, because the gate operator it runs takes the five locks itself and needs idle admission. Kind `gate` would hold both and refuse its own gate. So the kind runs one command only, built by `scripts/orchestration/driver-argv.sh`: `/usr/bin/env -i <session variables> /usr/bin/python3 -I -B $MAIN/scripts/orchestration/gate-run.py [--stop] <spec>`.
  - **Spec:** a canonical regular `.json` file under `$EP_ORCH` with a full `base` SHA.
  - **Code:** every entry of `scripts/orchestration` must be exactly BASE's, with BASE's bytes (`git hash-object --no-filters`, so `assume-unchanged` and `skip-worktree` change nothing). That binds the driver, its imports, the guard and the admission and outcome libraries.
  - **Refused with 64:** any other argument, script or interpreter; an override that names code (`BOUNDED_ADMISSION_LIB`, `BOUNDED_OUTCOME_LIB`, `BOUNDED_SPAWN`, `BOUNDED_CLASS`, `BOUNDED_LOCKS`, `BOUNDED_GATE_MEMORY_MAX`, `ADMISSION_TABLE`, `BASH_ENV`, `ENV`, `LD_PRELOAD`, `LD_AUDIT`, `PYTHON*`, `NODE_OPTIONS`/`NODE_PATH`); an exported function.
  - **Fixed PATH:** before either entry point sources, executes or looks anything up, it sets PATH to `DRIVER_PATH` in `$EP_ORCH/bounded-driver.sh`: the gate's `execution_tools` PATH, `/home/andreas/.nvm/versions/node/v22.22.0/bin:/usr/bin:/bin`. The caller's PATH is ignored, not validated. The unit, its sampler and receipt, and the driver run with that PATH, and Python always runs by absolute path. The guard refuses any other PATH, so an entry point that skipped the step never runs a driver.
  - **Neutralized:** the ambient session variables `GIT_*` and `LD_LIBRARY_PATH` (a T3 session sets `GIT_EDITOR` and `LD_LIBRARY_PATH`) are unset before any external command runs. Every git and Python call, and the driver itself, runs under `env -i` and never sees them.
  - **Order:** both entry points (`bounded.sh` and the unit's `run-bounded-driver.sh`) run as `bash -p`. `$EP_ORCH/bounded-driver.sh` checks the guard's bytes against BASE, under `env -i` with absolute tools, before sourcing it. The guard runs before either entry point loads any MAIN library or writes any state.
  - **`--stop` through the unit** needs MAIN still at BASE. After the checked fast-forward, run `gate-run.py --stop` directly. Until `$EP_ORCH/bounded.sh` has kind `driver`, start `/usr/bin/python3 -I -B $MAIN/scripts/orchestration/gate-run.py <spec.json>` with `systemd-run --user --collect --unit=ep-gaterun-<label> -p WorkingDirectory=$MAIN --setenv=PATH=/home/andreas/.nvm/versions/node/v22.22.0/bin:/usr/bin:/bin` and wait for the done marker.
- **Root still owns:** the diagnosis of a stop, recovery from an ambiguous state and every decision about a fresh attempt.

**Codex operator (transition).** Attempts prepared under a codex operator task before the script operator continue through that operator's frozen runtime: `export GATE_CONFIG=<its gate.json>; python3 -B "$GATE_ENTRY" resume`. `gate_core` accepts a codex operator task only for an attempt whose `prepared.json` binds that exact configuration. Every new attempt, `prepared`-mode retries included, uses the script operator. Root removes this paragraph once the first scripted gate has qualified the driver.

The driver writes one external JSON configuration with these fields (operations schema):

| Field | Contract |
|---|---|
| `version`, `kind` | `1`; `code` or `curation` |
| `main`, `orch`, `worktree`, `branch`, `feature` | Canonical absolute main/shared run/app checkout paths and exact Git branches |
| `base`, `reviewed`, `tree` | Full fixed Git SHAs, linear reviewed history on the frozen integration base |
| `attempt`, `label` | New absolute external evidence directory; safe unique invocation label |
| `operator` | `{path, sha256}` for the [script operator identity](#script-gate-operator) (enforced); a codex operator task only for an attempt already prepared under it |
| `author` | Separate `{path, sha256}` for the actual author task/model/options. Review independence is checked against the author. |
| `validation` | `{plan: {path, sha256}, receipts: {CHECK: {path, sha256}}}`: the validation plan and the original version-2 receipt for every reused check, verified at preparation, submission and final acceptance |
| `resourcePolicy` | `{path, sha256}` for the shared `resource-policy.md` |
| `storageBaseline` | `{path, sha256}` for the storage journal/counter baseline, in the existing guard format |
| `reviews` | Code: `standards` and `spec`; curation: `curation`, with all admissions reviewed |
| `phases` | Authorized subset of `prepare`, `submit`, `observe`, `collect`, `complete`, `checked-land` |
| `control` | Absolute external mutable stop control, bound to the operator's `taskId`/`runId` and reviewed/base/tree |
| `preparation` | `squash` or `prepared`, below |
| `issue` | Positive issue discriminator, curation only; independent of app branch/path |
| `remoteChecks` | Optional `{path, sha256, mode}`; [remote heavy checks](#remote-heavy-checks). Absent, every code path is the local gate. |
| `rebaseProof` | Optional, code only; [mechanical-rebase proof](#mechanical-rebase-proof) |
| `carriedReview` | Optional, code only; [single-axis fix review](#single-axis-fix-review) |
| `conditionalLand` | Optional, code or curation; [conditional LAND binding](#conditional-land-binding) |
| `lane` | Optional, code only; [light landing lane](#light-landing-lane). Absent, the full queue runs. |
| `preservedEvidence` | Optional `{path, sha256}` references to prior evidence; `kind: "index"` also verifies its relative `files` map at prepare/collect |

Each review declares `commit`, `tree`, `taskId`, `runId`, actual `target: {providerInstanceId, model, options}`, `task: {path, sha256}`, `report: {path, sha256}`, optionally `conditional: {path, sha256}` ([conditional LAND binding](#conditional-land-binding)), `disposition: "accepted"` and `unresolved: []`. A review binds `REVIEWED`/`TREE`, except as `rebaseProof`, `carriedReview` and `conditionalLand` allow. Task metadata must show the original run terminal and completed, with no pending children and exact model/options; the parent supplies these observations. A correction review's report carries prior acceptance and the delta/closure disposition. Record promotion also needs [T3 capture evidence](t3-reviews.md) and `catalog-record-review.ts --verify`.

New preparation: `preparation: {mode: "squash", archive: "refs/archive/RUN/reviewed", message: {path, sha256}}`. It keeps the reviewed chain under the archive, creates one exact-tree commit with the frozen base as sole parent, compares the complete content and records `mapping.json`. Curation must already be one specialized-prepared, reviewed commit; preparation keeps that commit and its prep receipt, and a mismatching prep receipt stops for fresh prep and review.

An already prepared candidate: `preparation: {mode: "prepared", archive: "refs/archive/RUN/reviewed", candidate: "FULL_SHA", mapping: {path, sha256}}`. The mapping binds `BASE`, `REVIEWED`, `TREE`, `WT`, `BR`, `ARCHIVE` and `SQUASHED`; historical mapping formats are read as they are, and tree, parent, diff, registered checkout and archive are rechecked. This creates fresh attempt evidence without re-squashing.

Control shape: `{state: "active", taskId: "ACTUAL_TASK", runId: "ACTUAL_RUN", reviewed: "FULL_SHA", tree: "FULL_TREE", base: "FULL_BASE"}`. Set `state: "stopped"` to stop; `finish-current` plus `phase` restricts continuation to that phase, except that finishing observation includes the required terminal collection, and completion waits for active continuing authority. The configuration authorizes the selected sequence once. Submission requires `observe`, `collect` and `checked-land` together, so a `finish-current` restricted to submission refuses before launch, and a run without submission authority can only prepare. A pause reports the actual blocked phase. After a claim, a refused control or validation handoff or an observer failure cancels only the invocation proven by the captured return and original claim. `cancel` bypasses the sequencing lock, and `cancel` and terminal `collect` stay available under stopped controls; cancelling after a canonical terminal receipt adds no retrospective stop marker. A deferred collection (`nextPhase: collect`) writes neither a failed result nor a stop marker. A failed, stopped or resource-failed invocation can neither complete nor resubmit. Every control, cancellation, deferral and recovery rule, verbatim: [control and cancellation](../orchestration-reference/gate-operator-internals.md#control-and-cancellation).

The driver runs these commands; root runs them by hand only for the codex transition or a recovery it has diagnosed:

```bash
export GATE_CONFIG=/absolute/ep-orch/run/gate.json
python3 -B "$MAIN/scripts/orchestration/gate-operator.py" prepare
GATE_ENTRY=$(python3 -B "$MAIN/scripts/orchestration/gate-operator.py" runtime)
# Retain this absolute attempt entry before the queue can change MAIN.
python3 -B "$GATE_ENTRY" resume
```

Use the retained `$GATE_ENTRY` for every later `resume`, `collect`, `cancel`, `complete` or repeated `run`. `runtime` returns it only after successful preparation; an initial `run` prepares and re-executes it automatically (`attempt/operator-runtime/gate-operator.py`). `run` chains a fresh authorized attempt; `resume` reuses a completed preparation and its saved invocation. A create-only claim precedes the only submission. Lost or ambiguous returns, failures, identity drift, unexpected controls and resource violations stop the chain: inspect the existing invocation instead of resubmitting it. Failures follow [Authorization and failures](decisions.md#workflow): a live gate failure, resource violation or observer safety event keeps its failed receipts and needs diagnosis before a fresh attempt; partial launched attempts remain historical. Full entry and chaining contract: [runtime entry](../orchestration-reference/gate-operator-internals.md#runtime-entry-chaining-and-failures).

Collection references the canonical receipts, logs and original-suite JSON. A failed receipt, stopped monitor, missing resource observation, non-green original suite or incomplete checked landing cannot finalize (a unit deactivating after a clean exit is terminal, its counters unavailable rather than missing: [monitor provenance](../orchestration-reference/qualification.md#monitor-provenance)); LOAD/NEW verdicts never authorize landing. Host, storage and Docker guards, caps, admission and locks stay binding. A new runtime or script version needs qualification before live use. Run the runner/receipt/transition fixtures and the shell queue, prep, pair, admission and triage fixtures with `pnpm -s test:workflow`, which gate CI's static job also runs. Full collection contract: [submission and collection](../orchestration-reference/gate-operator-internals.md#submission-and-collection).

### Gate time

Every gate measures its own work time against the median of the last five landed gates of its mode and refuses to land more than 30% over it (owner rule 2026-11-08, [decisions](decisions.md#workflow)); `scripts/orchestration/gate_time.py` holds the rule and `gate-time.test.py` its fixtures.

- **Mode:** `curation` for every curation gate, then `light` (the light lane), `replace`, or `local` (local and `compare`).
- **CI part:** the remote manifest's run, as its longest job's execution, `startedAt` to `completedAt`. It is read from GitHub, `gh run view <runId> --attempt <attempt> -R <repository> --json jobs`, because the manifest holds command times, not job times. Skipped jobs and the assembly job (the manifest runner's `job`, `remote-checks`) are left out, unless the assembly is the run's only job (CI before the shards). A gate without remote checks has no CI part.
- **Host part:** the driver's stage seconds without the wait stages (`prelaunch`, `admission-probe`) and the measurement itself (`gate-time`), less every wait inside `resume`. The gate operator passes the attempt's wait ledger (gate.json `gateTime.waits`, `<attempt>/gate-waits.tsv`) to the queue as `LAND_GATE_WAITS`. `land-queue.sh` writes `started<TAB><epoch>` there as it starts in the unit, and every blocking wait the queue can reach runs through `gate_wait <label> <command>` (`paths.sh`), which appends `wait<TAB><label><TAB><seconds>`. The waits left out:
  - **launch:** the submission claim's `at` to the queue's start: `bounded.sh`'s lock wait (resource, curator, curator2) and admission wait (`BOUNDED_WAIT=1`, up to 1,800 s), and the unit's start;
  - **land.lock:** `land-queue.sh`, and `cur-land.sh` when it runs outside the queue;
  - **heavy.lock:** `triage-failures.sh` (the full suite) and `host-audits.sh`;
  - **memory:** a curation prep's escalation (`cur-prep.sh`, `admission.sh escalate`);
  - **landing observation lock:** `land.sh`, after the land check, so only the result's total leaves it out.

  `prepare` and the submission take their locks without waiting (a held lock refuses at once), and the operator's observer runs beside the queue. `QueueWaitCorpusTest` (`gate-time.test.py`) scans every orchestration script: each blocking `flock`, memory escalation and Python `fcntl.flock` without `LOCK_NB` either goes through `gate_wait` or is named there as never inside a gate's queue (admission.sh's mutex, the WIP CI slot, the driver's publication lock). A ledger the queue cannot write stops the script, and an unreadable ledger or claim refuses the land check (`test_an_unreadable_wait_ledger_refuses`). Fixtures: `test_a_long_launch_or_lock_wait_is_left_out_and_does_not_refuse`, `test_a_long_launch_and_lock_wait_is_left_out_of_the_host_part`, `cur-land.test.sh` ("waited") and `land-queue.test.sh`.
- **Baseline:** exactly the last five landed results of the same mode among `R/*-gate-r*-result.json`, in landing order (`endedAt`, newest first); a result older than them is never read. Each one gives its `gateTime` total; a lower-bound total (`totalLowerBound`) gives its recorded host part plus its manifest's GitHub run. The trigger is 1.3 times the median total (`test_five_new_format_results_give_the_baseline`). Neither case below refuses, and building the baseline never raises or stops the gate (`test_a_baseline_that_cannot_be_built_is_unavailable_and_never_raises`):
  - **fewer than five:** "no baseline";
  - **the five cannot be told, or one of them gives no wait-free gate time:** `baseline unavailable (<result>: <why>)`, listed under `unreadable`. That is: any result in R that is unreadable, not a JSON object or without a verdict, or a landed one whose mode or landing time cannot be read (it could be one of the five); or one of the five that lacks gate-time fields, lacks its recorded waits (`host.waits`, every row a label and seconds) or, for a lower-bound total, whose GitHub run cannot be read again. Every result from before gate-time-check lacks the fields, whatever its logs show: its stage seconds hold untimed waits. A sixth gate never takes a place. The table of these inputs is `test_every_past_result_the_rule_cannot_read_makes_the_baseline_unavailable_and_never_refuses`. So no gate refuses until five results with gate-time fields have landed in a mode; until then root keeps its hand check before each gate (root's ruling, gate-time-check fix r2).
- **The measure is the total** (root's ruling, 2026-11-08). Every check judges the gate's total own time against the median total; outside causes are noted, never counted.
- **CI fail fast, before prelaunch** (the `gate-time` stage): a gate whose CI part alone is already over the total trigger (1.3 times the median total) cannot pass, so it stops there: `Gate time refused: gate time (CI part) N s is X% over the M s median of <mode>`. Any other CI part waits for the total check. The CI part against the median CI part of the baseline gates is recorded as `ciInformation` and refuses nothing. Fixtures: `GateTimeTest` in `gate-run.test.py`.
- **Unreadable CI part** (gh fails or times out, or the run has no timed job): an outside cause. The result records `ci: {unavailable: <reason>}` and never refuses for it. The total is the host part alone, judged as a lower bound and marked `totalLowerBound` (`at least N s` in the Markdown and in the land-check line). Fixtures: `test_an_unreadable_ci_part_never_refuses_and_the_host_part_is_a_lower_bound`, `test_an_unreadable_ci_part_judges_the_host_part_alone_as_a_lower_bound`.
- **Total check, just before `land.sh`:** the driver writes `gate-time.json` as `resume` starts: the CI part, the host part so far, the moment `resume` started, the baseline and the outside cause. gate.json's `gateTime.path` names it and the gate operator passes it to the queue as `LAND_GATE_TIME`. `cur-land.sh` runs `gate_time.py land` after every other stage and its last identity check, immediately before `land.sh`, logging to its `gate-time` stage log. The total there is the CI part plus the host part up to that moment, less the waits recorded so far; the line names them (`waits N s left out`). More than 30% over the median total refuses: `gate time refused (see <log>); not landing`, and the driver's stop reason is `Gate time refused: gate time N s is X% over the M s median of <mode>`. Fixtures: `cur-land.test.sh` ("gate time just before land.sh") and `test_the_queues_land_check_refusal_is_the_stop_reason`. The result's total also counts the time after `land.sh` (collection and completion), so it can be larger than the total the check judged.
- **Outside cause:** only root records one, as the spec key `gate_time_exempt: {"reason": "<text>"}` (through `brief.py --extra`, or on a retry `gate_config.py retry ... --extra '{"gate_time_exempt": {"reason": "<text>"}}'`; `gate_config.py` refuses any other shape, and a retry spec keeps the prior one). With it a trigger is recorded with the reason and the gate goes on; the verdict is `exempt`.
- **Widen first:** a spec without the key and a mode without a baseline still run; a candidate's queue runs the total check only when the gate operator passes `LAND_GATE_TIME`.

## Remote heavy checks

A verified Boat run of typecheck, lint and the full suite for the exact candidate tree may count for the landing gate (owner 2026-10-30). Boat publishes `$EP_ORCH/remote-checks/<runId>/` with `manifest.json` last and the directory read-only; the orchestrator names the manifest in `gate.json` as `remoteChecks: {path, sha256, mode}`. A remote skip counts only for a test on the pinned host-audit list, `scripts/orchestration/host-audits.json`, whose sha256 the manifest binds (owner 2026-11-02): those tests need sources only the gate host has. `replace` skips the local typecheck, lint and suite and runs the listed tests on the gate host (`host-audits.sh`), which must all pass; `compare` runs them all and requires the same per-test results and totals outside the list, with every listed test passed locally. Root publishes the candidate with `gate-push.sh` as a parentless commit of its tree carrying `Gate-Reviewed`, `Gate-Base` and `Gate-Tree` trailers (owner 2026-11-02); the integration history is never pushed, the verifier binds the trailers, and ancestry is checked on the gate host. `scripts/orchestration/remote_checks.py` is the verifier; the bindings are in [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks).

- **Stop conditions:** a refused push, a remote commit that is not the tree-only gate commit for `REVIEWED` (or the prepared squash) on `BASE`, a remote failure, a refused or stale binding (tree, base, lockfile, host-audit list, toolchain, timezone, environment, argv, completion, suite or file set), an unlisted remote skip, a listed test missing from the remote report, in `replace` a listed test not passed on the gate host or, in `compare`, any difference outside the list or a listed test not passed locally blocks landing; there is no fallback to a local or partial pass.
- **CI shards** (owner 2026-11-06): a `gate/<label>` push runs `ci.yaml`'s gate jobs on GitHub's free `ubuntu-latest` runners: 11 `remote-shard` jobs (each `--shard=i/11` of the suite, `VITEST_MAX_WORKERS=2`, dealt by recorded duration with Chromium's tests in shard 1 alone, `tests/shard-plan.ts`), `remote-static`'s two legs (`checks`: install, typecheck and lint; `workflow`: install and `pnpm -s test:workflow`, recorded as the manifest's `workflow` row with the leg's facts as `workflowJob`) and `remote-checks`, the assemble job, which runs even when a part failed, merges the shards' blob reports into `full.json` and uploads the one `remote-checks-<runId>` artifact that `remote-fetch.sh` fetches. It fetches it from the push run on `gate/<label>` that produced it, never from a WIP run, and records that run in `provenance.json`; the verifier refuses a manifest without it ([gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks), "Separation from WIP CI"). A missing, empty, failed or mismatched shard, a part from another run attempt, a producer job that did not succeed, or a merge that is not exactly its shards, is refused at the gate; the single-job manifest shape is refused. Parts are named for the run attempt, so after a failure use GitHub's *Re-run all jobs*: re-running only the failed jobs leaves this attempt without the other parts and refuses. The shard count appears in the matrix and both `--total` arguments; `remote-ci.test.py` holds them equal. The gate runs 13 jobs at once (N shards and two static legs), one WIP run at most 6 (5 shards and `wip-static`) and `wip-sweep.yaml` 1, within the Free plan's 20; `remote-ci.test.py` counts them from the `needs` graph. To retune, regenerate `tests/shard-weights.json` with `scripts/orchestration/shard_weights.py <fetched run directory>`; `tests/shard-plan.test.ts` holds the slowest projected shard under 10 min. Details: [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks).
- **Static job and widen then narrow** (gate-ci-workflow): `test:workflow` runs in CI on every gate push, so a stale pin or broken fixture in the orchestration suite fails the gate's static job, not a later review. A test there must run on a runner from the depth-1 gate checkout, with no `$EP_ORCH`, no gate-host sources and no git identity. One that needs gate-host sources prints `SKIP (host-only: …)` naming them. A verifier or producer contract change lands widen then narrow, because MAIN's verifier and the candidate's must both accept the landing's manifest. The `workflow` row is optional while `remote_checks.REQUIRE_WORKFLOW` is False. The follow-up `t3/gate-ci-workflow-require` sets it True once this slice is MAIN's. Likewise the workflow leg's `workflowJob` and `workflowInstall` (speed-ci-static-split) are required since static-split-narrow, and a manifest without either is refused, naming the key (`remote-checks.test.py` `test_the_workflow_legs_facts_and_install_row_are_required`). Details: [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks).
- **Host audits during CI** (owner 2026-11-07, `$EP_ORCH/mvp-20261023/owner-decision-20261107-blacksmith-thresholds-audits.md` item 3, replacing the 2026-11-02 in-gate contract): a `replace` gate may take its host audits from a receipt that root's `host-audits.sh --receipt` wrote while CI ran, on the pushed gate commit. The receipt binds the tree, base, audit list sha256, lockfile, toolchain, sources, verdict and report. The spec's `host_audits_receipt: {receipt, sha256}` becomes `gate.json` `hostAuditsReceipt`; the driver's precheck, every authorization, the queue (in place of `host-audits.sh`) and collection verify it. Any tree change invalidates it, CI green on the same exact tree is still required, and any mismatch stops the gate with its reason rather than running the audits. A local or `compare` gate refuses a receipt. Without one, `replace` runs `host-audits.sh` in the gate as before: the fallback while the receipt path is widened. Details: [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks).
- **Push path:** `gate-push.sh` builds its commit and pushes through `scripts/orchestration/push-lib.sh` in gate mode (`gate/**` only); the library pushes a full-SHA parentless commit to the one checked origin URL as `refs/heads/<mode>/<name>` (mode `gate` or `wip`), never forced, never over a ref at another commit, and `push-guard.test.sh` (in `test:workflow`) refuses every other ref.
- **Trust:** the manifest and its files are writable local artifacts pinned by sha256 in `gate.json` and the queue argv. This detects corruption, moved directories, stale scope and unsupported pass claims; it is not cryptographic attestation against an actor rewriting every file.
- **Curation:** a curation gate with remote checks binds its remote-suite prep receipt, `cur-<n>-prep.remote.receipt` from `cur-prep.sh --remote-suite` ([validation evidence](#validation-evidence)), pinned in `gate.json` and joined at every authorization with the gate's issue, `REVIEWED`, `TREE` and `BASE`; the manifest's `Gate-Reviewed` must be `REVIEWED`. Any amend of the prep commit needs a fresh remote-mode prep and push. Details: [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks).
- **Not supported:** pairs, more than one queue item and author validation receipts. The gate unit keeps its memory cap and admission in every mode.

**WIP CI jobs** (owner 2026-11-06, speed-wip-ci W2): a `wip/<task>-<stamp>` push runs `ci.yaml`'s `wip-*` jobs instead of `checks`. They are information for the worker and never landing evidence: no `wip-*` job runs `remote_ci.py`, writes a manifest or uploads a `remote-*` artifact, and `gate.json` has no field for them. `wip-plan` reads the pushed commit's `Wip-Scope` trailer through `scripts/orchestration/wip_ci.py`: `suite` alone, or `tests/<dir>` directories that exist, reached through no symlink and holding a test file, plus `static=yes|no` (default no); any other scope fails the plan and the summary says why. `wip-shard` runs Vitest's `--shard=i/8` of that scope, five at a time (speed-ci-static-split: beside the gate's 13 jobs and the sweep's 1), with the gate's pinned environment; `wip-static` runs typecheck and lint when asked. `wip-summary` always runs and uploads `wip-summary-<run_id>`, kept 3 days: `wip-summary.json` (`wip-ci-summary-v1`: the source, each shard's exit, duration and counts, each failure's first 30 lines, the 20 slowest files, a failed static command's last 40 lines) and `wip-summary.md`, at most 200 lines and 16 KB, which is also the run's step summary. Every WIP job reads contents only, gets no secrets and stops at 40 min. `wip-ci.test.py` and `e2e/support/ci-workflow.test.ts` hold this shape. No WIP artifact, run or ref is accepted as gate evidence: [gate modes](../orchestration-reference/gate-modes.md#remote-heavy-checks), "Separation from WIP CI".

**WIP CI runs** (speed-wip-ci W3): from the worktree, in the background (`run_in_background` or `t3_background_wait`), run `scripts/orchestration/wip-ci.sh run [--scope <suite|tests/dir ...>] [--static] [--timeout 45m]`. It needs no `capped.sh` slot. `--scope` defaults to `suite`. `--task` defaults to the last part of the branch name, and `--base` (`Wip-Base`) to the merge base of HEAD and `feature/pf1-character-builder`. `--timeout` is at most `60m`. `wip-ci.test.sh` covers each step below against a bare local origin and a stub `gh`.
- **Snapshot:** a copy of the worktree's index takes every file the worktree holds, uncommitted and untracked ones included, with `.gitignore` applied. It becomes a parentless commit with the trailers `Wip-Task`, `Wip-Base` and `Wip-Scope`, which `wip_ci.py plan` accepts. The worktree's own index, refs and stash stay as they were, while the run runs as well as after it. A scope that `wip_ci.py` would refuse exits 64 before anything else.
- **Refusals** (exit 1, nothing pushed, `gh` never called): an `.env*` file other than `.env.example`, anything under `e2e/.private`, a file of 100 MB or more, a `.github/` change against `Wip-Base`, an index entry marked assume-unchanged or skip-worktree (in a 6,000-entry index too), and the origin checks of `push-lib.sh`.
- **Slot:** one WIP run at a time, `flock` on `$EP_ORCH/wip-ci/slot`. A second run waits up to 20 min, then exits 75 without pushing. No child process keeps the lock, so the slot is free as soon as the wrapper ends, even after a KILL.
- **Push:** through `push-lib.sh` in wip mode (`push-guard.test.sh`), only `<commit>:refs/heads/wip/<task>-<stamp>`. It never forces and never pushes tags, whatever `push.followTags`, `push.default` or `remote.origin.push` say. A ref already at origin under that name is refused and left alone. The push and the delete run from a scratch bare repository that borrows the worktree's objects and has no remotes, so no `refs/remotes/*` ref is written. A relative origin (a local path such as `../origin.git`) is resolved against the worktree first. The push and the delete each run under their own 15 min cap, apart from `--timeout`, since pushing this tree takes minutes: a push past it exits 1 and a delete past it exits 3, each saying it timed out.
- **Watching and results:** the wrapper prints the run URL and polls `gh run view` every 30 s. Every `gh` call, the download included, runs under `timeout` for what is left of `--timeout`, so a stalled call neither delays the 124 nor holds back cleanup after a signal. It downloads `wip-summary-<run>` to `$TMPDIR/wip-ci/<run>/` and prints `wip-summary.md`, whole lines only, at most 200 lines and 16 KB, then the path of the full file.
- **Cleanup:** on a timeout, TERM, HUP or INT, the wrapper first cancels its run (`gh run cancel`, at most 20 s). On green, red, timeout, TERM, HUP or INT, it then deletes its branch while origin still holds its commit there, then releases the slot. If the deletion fails, it exits 3 and names the branch it left for `wip-sweep`. INT reaches the trap only where the shell has not ignored it: a background job of a non-interactive shell starts with INT ignored, so the test restores INT's default, as a foreground run has it.
- **KILL:** no process can clean up after SIGKILL. The slot is free at once, because no child keeps the lock. The branch stays at origin as `wip/<task>-<stamp>`, which `wip-sweep` removes once it is more than 6 h old (root's disposition, 2026-11-07); `wip-ci.test.sh` asserts that the branch stays and has that name.
- **Exit codes:** 0 green (the run succeeded and the summary says green), 1 red (anything else, the summary missing included), refused or a push past its cap, 124 timeout, 75 no slot, 64 usage, 143 after TERM, 129 after HUP and 130 after INT, and 3 when the branch could not be deleted (it replaces any of these; the result line printed before it still says green or red).
- **The one push path:** `push-scan.test.sh` refuses `git push` in any tracked file outside an explicit allowlist: `gate-push.sh`, `wip-ci.sh` and `push-lib.sh`, the git-guardrails hook that names it to block it, Markdown, comment lines and the scan's own fixtures. It catches a shell command (options before `push`, including a quoted `-C` path with spaces, and continuations) and an argv list on one line or several (`'git', '-C', root, 'push'`); a push built in a string, an alias or a variable is out of its scope. `wip-sweep.sh` has no push command of its own: it deletes through `push-lib.sh` in wip mode (`wip-sweep.test.sh` checks both).

**WIP sweep** (speed-wip-ci W4): `.github/workflows/wip-sweep.yaml` runs every hour and on `workflow_dispatch` (input `dry-run`). GitHub runs a scheduled workflow only from the default branch's copy. It deletes each `refs/heads/wip/<task>-<stamp>` branch at origin whose stamp is more than 6 h old: the branch a KILL leaves, or one whose deletion failed (exit 3). `e2e/support/ci-workflow.test.ts` holds its shape: one job, `contents: write` and nothing else (the only `contents: write` grant in the workflows), no secret but the job's own token, no push trigger, and one step that runs `scripts/orchestration/wip-sweep.sh`.
- **Only `wip/`:** the script lists only origin's `refs/heads/wip/*` and deletes through `push-lib.sh` in wip mode: only `refs/heads/wip/<name>` (`[a-z0-9-]+`), and only while origin still holds the listed commit there.
- **Unknown age:** a `wip/` branch whose name has no wip-ci stamp (`<task>-YYYYmmdd-HHMMSS`, UTC) has no known age; it is left, and named in the output.
- **Exit codes:** 0 done, 1 a listing or a deletion failed (each other branch is still swept), 64 usage. `--dry-run` prints what it would delete and deletes nothing.
- **Tests:** `wip-sweep.test.sh` (in `test:workflow`) runs it against a bare local origin holding a fake ref list with ages. It deletes exactly the branches over 6 h old and keeps one at exactly 6 h. Nine refs outside `refs/heads/wip/`, eight with old stamps in their names, are neither touched nor named. A dry run deletes nothing. A refused deletion exits 1, and a later sweep deletes the branch.

## Mechanical-rebase proof

A rebase-only change is a mechanical check, not new reviews (owner 2026-10-31). Run `python3 -B scripts/orchestration/rebase-proof.py WT OLD_BASE ACCEPTED NEW_BASE` (full SHAs; clean WT whose `HEAD` descends from NEW_BASE; `--head SHA` reads objects only). On PASS it prints `{verdict: "PASS", ..., rebaseProof}`; put `rebaseProof: {oldBase, accepted, acceptedTree}` into `gate.json` as is, and Standards/Spec reviews bound to `(accepted, acceptedTree)` count. The gate re-proves it from Git objects at every authorization: equal per-commit deltas and messages, equal commit count and equal net delta on both bases.

- **Refusals:** any overlap between the slice and the base movement, an unmoved base, a changed commit or message, a different net delta, a missing object or no review binding `accepted`. A refusal means full independent reviews of the rebased head; there is no fallback. Every refusal and its message: [gate modes](../orchestration-reference/gate-modes.md#mechanical-rebase-proof).
- After repeated rebases, prove from the original accepted commit straight to the current head, and keep `accepted` reachable with an archive ref (for example `refs/archive/RUN/<slice>/accepted`).
- The full gate suite stays authoritative for semantic interaction, which no textual proof can see.
- **Not supported:** curation, pairs and overlap.

## Single-axis fix review

When only one axis had findings, only that axis (A) re-reviews the fix; the other axis's (B) LAND stands unless the fix touches behaviour it judged (owner 2026-10-31). `gate.json` carries `carriedReview: {axis, commit, tree, attestation: {path, sha256}}`: B's review at the earlier commit E = `commit`, together with A's fix review at the head H.

- A's report must contain the literal `E..H` with full SHAs, and E must lie strictly inside the linear chain from the frame base to H (`gate_core.carry_proof`).
- Root writes the attestation JSON with exactly `{version: 1, axis: B, carried: E, head: H, paths, statement, attestedBy}`. `paths` is `git diff-tree -r --no-renames --name-only -z E H`, sorted (as `carry_proof` returns it); `statement` is root's judgement that the delta stays within A's findings and touches no behaviour B judged.
- **Composition:** fix first, rebase last. Fix-then-rebase composes with `rebaseProof`; rebase-then-fix refuses, and B then gets an ordinary delta review.
- **Refusals** (each with its own message, no fallback): a malformed field, a curation kind, E outside the chain, a report without the full-SHA delta, an attestation mismatch, or B not bound to `(E, tree)`. The full list: [gate modes](../orchestration-reference/gate-modes.md#single-axis-fix-review).
- **Not supported:** curation, pairs and rebase-then-fix. A fix broader than the findings goes to both axes.

## Conditional LAND binding

A review's "LAND once X is fixed" with a machine-checkable X binds at the reviewed commit E together with the repaired head H, with no further review round (owner 2026-11-04). `gate.json` carries `conditionalLand: {axes, commit, tree, paths, message, attestation: {path, sha256}}` (gate spec: `conditional_land`, with `attestation` and `attestation_sha256`; each conditional review entry names its `conditional` file).

- **Git:** H is `REVIEWED` (or, with `rebaseProof`, `accepted` on the old base). E lies strictly inside the linear chain from the frame base to H, or E is an amend of H's tip, sharing H's only parent (a count or a curation prep commit's message repaired in place). The delta `git diff-tree -r --no-renames --name-only -z E H` must be exactly the named `paths`, and an amend changes the commit message exactly when `message` is `true`.
- **Reviewed scope:** a reviewer who answers conditional LAND writes a separate `<axis>-conditional.json` next to the report, exactly `{version: 1, verdict: "land-once-fixed", reviewed: <full E SHA>, paths: [...], message: true|false, check: "<command or expected value>"}`, and the review record binds it as `conditional: {path, sha256}`. Only these files grant scope; report Markdown is never parsed for it. The repair must lie inside the union of the listed reviews' files, and the configuration and attestation can narrow it but never widen it.
- **Attestation:** root writes exactly `{version: 1, kind: "conditional-land", axes, commit: E, head: H, relation, paths, message, check: {command, output, commit}, statement, attestedBy}`. `relation` is `descendant` or `amend`; `check` is root's mechanical check of X at `REVIEWED`: the command, its output and the commit.
- **Refusals** (each with its own message, no fallback): a malformed field, a combination with `carriedReview`, E = H, E outside the chain and not an amend of its tip, a merge, a broader or narrower delta, a path outside the named set, an unnamed or absent message change, no listed review binding a conditional file, a file bound to an unlisted review, a missing, changed or malformed file (keys, verdict, `reviewed`, paths, message, check), a `reviewed` other than the bound commit and E, a repair outside the reviewed scope, and a missing, edited or disagreeing attestation. The full list: [gate modes](../orchestration-reference/gate-modes.md#conditional-land).
- **Not supported:** pairs, `carriedReview` together with it, and rebase-then-fix.

## Light landing lane

A candidate whose every changed path lies outside everything the full queue reads skips the full gate (owner 2026-11-01, bounded risk: a dependency the lane missed fails the next full gate, which always follows on a tree that includes the change). `gate.json` carries `lane: {mode: "light", rule: "light-lane-v1", paths}`, pasted from `python3 -B scripts/orchestration/light_lane.py check ROOT BASE COMMIT`. It skips codegen, the pin, typecheck, lint, the full suite and the E2E preflight; identity, review binding (with `rebaseProof` and `carriedReview` unchanged), the exact-tree squash, the bounded unit, rebase, `pnpm install --offline`, the writer check, `check:artifacts`, checked `land.sh`, collect and complete still run.

- **Rule** (`light_lane.py`, from Git objects only): only added or modified mode-100644 files, all on the allowlist (`AGENTS.md`, `CLAUDE.md`, `docs/standards.md`, `.claude/settings.json`, `.gitignore`; `*.md` under `docs/agents/`, `docs/product/` and `.agents/skills/`; `.claude/agents/<name>.md`); no non-Markdown reference to a changed path outside the reviewed `REFERENCES` table; unchanged pinned readers; `.gitignore` only gains blank lines, comments or literal `.claude/` paths.
- **Light checks:** each changed `.json` parses strictly, and each relative link on an added line of a changed `.md` resolves in the commit (`http:`, `https:`, `mailto:`, `#`, absolute, `$` and `<` targets skipped). A light-check failure (exit 2) is a fix round.
- **Refusal** (exit 1): the full gate now; the operator writes a config without `lane`. A `reader pin changed` refusal or a new census hit means the same. Updating the rule (pins, allowlist or `REFERENCES`) is its own reviewed workflow slice.
- **Read lock:** every full gate that runs its suite locally through `triage-failures.sh` runs it under `lane-lock.sh`, which makes every tracked lane-eligible file except `.gitignore` unreadable to the suite. `.gitignore` is never locked and stays readable (git must read it); R5 bounds its changes instead. A `remoteChecks` gate in `replace` mode runs no local suite, so the lock does not apply to it. If the lock process dies before restoring (a `lane-lock-<report>.json.active` record beside the triage report), recover as [gate modes](../orchestration-reference/gate-modes.md#light-landing-lane) describes before any fresh attempt.
- **Not supported:** curation, pairs, `remoteChecks` and more than one item; `README.md`, `GLOSSARY.md` and non-Markdown files under `.agents/skills/`.
- Full rule, stop messages, why each skipped stage is safe and what is not guaranteed: [gate modes](../orchestration-reference/gate-modes.md#light-landing-lane).

## Protected refs

Root, 2026-11-07 (gate-hold-scope; `$EP_ORCH/mvp-20261023/speed-gate-review.md` §3): a gate protects only its own refs, so workers keep working while it runs. Exact rule and evidence: [gate modes](../orchestration-reference/gate-modes.md#protected-refs).

- **Protected; a move stops the gate (`protectedRef`):** the gate's branch `refs/heads/<BR>`, the integration branch `refs/heads/<FEATURE>`, the reviewed archive `ARCHIVE`, `refs/heads/main` and every `refs/archive/**`. Each may move only as the gate moves it. Other archives may be added, but once a row has seen one it is never rewritten or deleted.
- **Recorded only:** every other ref. A worker's commit on its own `t3/*` branch, a T3 checkpoint under `refs/t3/` and a `git fetch` (`--prune` included) that moves `refs/remotes/*` appear in the row's `otherRefMoves` and never stop the gate.
- **Row evidence** (gate-ref-digest; `$EP_ORCH/mvp-20261023/speed-gate-review.md` §5): preparation stores every ref once, in `protected-refs.json`. Each observer row carries a digest of the protected refs (`protectedRefs`) and of the rest (`otherRefs`), plus only the refs of each set that moved since the previous row (`protectedRefMoves`, `otherRefMoves`). A row where nothing moved carries the two digests only. The judge rebuilds every ref at each row from the snapshot and the moves, so the protected-ref rule judges what it judged on rows that listed every ref (`gate-monitor.test.py` `test_reconstruction_equals_the_old_full_rows_on_a_recorded_fixture`).
- **A ref record that does not rebuild refuses:** a move from a value the previous row did not have, a move filed under the wrong set, a set that does not match its digest, or rows of both forms in one invocation. Live, that is an observer failure; at collection, a `resources` error (`gate-monitor.test.py` `test_a_tampered_move_or_digest_refuses_the_rows`, `gate-operator.test.py` `test_the_streamed_scan_matches_the_whole_file_read`). Rows written before this change list their refs under `refs` and are judged as before (`test_rows_that_carry_every_ref_are_judged_on_the_protected_set`).
- **Still a stop:** another session in the gate's worktree. A commit, an edit or a checkout there fails the row's identity check or the integrity worker's `check_identity` (the ci-shards r2 stop).
- **Automatic Git maintenance off, required:** in MAIN and in every one of its worktrees, Git must resolve `gc.auto=0` and `maintenance.auto=false`. That reading takes in every layer and include Git applies there: a worktree's `config.worktree`, `includeIf` `gitdir:` and `onbranch:`, and the user and system files. Scheduled maintenance must also be off: no `maintenance.repo` entry that reaches MAIN's object store, no active `git-maintenance@*` systemd user timer, and no crontab line that runs it. Root set both settings once, on 2026-11-07, in MAIN's shared repository config, with `git -C MAIN config gc.auto 0` and `git -C MAIN config maintenance.auto false`; every worktree inherits them unless it overrides them, and `git config --unset` reverses them. With anything still on, the driver stops at its identity stage and preparation refuses at its prelaunch row, each naming the worktree. On every observer row a worktree, including one added during the run, that reads maintenance as on stops the gate (`automaticMaintenance`). Workers must not override either setting in their own worktree's config. A worktree entry Git cannot resolve (prunable, vanished, or locked mid-creation) also refuses, unless it is a scratch checkout the attempt itself recorded ([gate modes](../orchestration-reference/gate-modes.md#protected-refs)). So never move a worktree by hand: use `git worktree move`. Root removes any stale `ep-gate-*` scratch before a gate.
- **Object-store maintenance, forbidden by rule:** `git gc`, `repack`, `prune` (of objects), `prune-packed` and `maintenance run` run only outside gates, by hand. The monitor cannot see a manual run, so the rule binds every session, root included. `git worktree prune` is allowed: it removes only the administrative entries of worktrees whose directories are gone and never touches objects or refs, and the gate's own cleanup runs it (`host-audits.sh`, `triage-failures.sh`).
- **What root no longer pauses:** workers' commits on their own branches, their fetches and their editors. Heavy commands already queue behind a gate: the gate holds the resource, curator and curator2 locks and needs idle admission, and `capped.sh` queues behind a waiting gate.
- **Which monitor judges:** the attempt's frozen `operator-runtime`, copied from MAIN at preparation. A gate prepared on a MAIN without this rule keeps the every-ref rule for its whole life, resumes included, so root pauses workers for that gate.

## Gate memory

The gate unit's `MemoryMax` (`$EP_ORCH/bounded.sh`, kind `gate`, no MemoryHigh) depends on the gate mode. A gate launches only with its mode's launch allowance plus the 6 GiB in-run host floor available; below the floor for 5 s, a running gate stops:

| Gate (`gate.json`) | Cap | Launch allowance | Launch guard | Root's pre-check and the driver's prelaunch sample |
|---|---|---|---|---|
| local (no `remoteChecks`, light lane included) or `remoteChecks.mode` `compare`: the local full suite runs | **15 GiB** | 11.5 GiB | **17.5 GiB** | 18.0 GiB ×3 |
| `remoteChecks.mode` `replace`: no local typecheck, lint or suite | **10 GiB** | 8.5 GiB | **14.5 GiB** | 15.0 GiB ×3 |

- **One source:** `gate_monitor.py` holds both per-mode values. `GATE_MEMORY_MAX_BYTES` holds the caps; for the gate's mode they set the unit's real-memory stop and the expected unit `MemoryMax`. `GATE_LAUNCH_ALLOWANCE_BYTES` holds the allowances, and `launch_minimum_bytes` adds the floor. Every launch check takes the guard from there: the monitor's launch row, the driver's post-preparation check, and the driver's prelaunch sample at the guard plus 0.5 GiB (`gate-monitor.test.py` `test_launch_needs_the_mode_allowance_plus_the_host_floor`; `gate-run.test.py` `test_memory_guard_stops_before_preparation`, `test_post_preparation_memory_below_the_launch_guard_stops_before_submission` and `test_replace_mode_samples_at_its_own_launch_guard`). A value between the new and the old guard launches (the `between` tests there).
- **Why the allowance (owner, 2026-11-07):** owner apps keep MemAvailable at 15.1–15.9 GiB while the PC is in use, so the old guards (the cap plus the floor: 16 and 21 GiB) held W1's gate once and W2's three times on memory alone. The replace allowance is the 8.13 GiB cold-cache peak rounded up (13 replace gates peaked at 7.34 GiB kernel); the local and compare allowance is the measured 10.07 GiB peak plus margin (`$EP_ORCH/mvp-20261023/owner-decision-20261107-gate-thresholds.md`). The caps stay the OOM boundary, and the floor stop is unchanged (`gate-monitor.test.py` `test_each_mode_has_one_named_cap_and_a_launch_guard_of_its_allowance_plus_the_unchanged_floor`, `test_in_run_host_floor_stays_six_gib_for_five_seconds`).
- **Disk floor (owner, 2026-11-08):** on 2026-11-08 `df` showed 11 GiB free while btrfs metadata was full, and writes failed with ENOSPC (`$EP_ORCH/mvp-20261023/incident-20261108-btrfs-metadata-enospc.md`). `disk_guard.py` holds the floors and reads the volumes, read-only and without sudo: free data (statvfs) at least 15 GiB and, on btrfs, the metadata headroom (`allocation/metadata` total less used, less `global_rsv_size`, from `/sys/fs/btrfs/<fsid>`) at least 1 GiB unless at least 2 GiB of the device is unallocated, since metadata grows into it. A non-btrfs volume has only the data floor. A part it cannot read is unavailable with its reason: it prints a warning and never blocks on its own (`disk-guard.test.py`).
  - **Gates:** the prelaunch reads the volumes of `$EP_ORCH` and MAIN for each sample; a volume below a floor is a `disk` blocker beside memory, and disk alone stops the prelaunch after 30 minutes with a `Disk guard:` reason, as memory alone does (`gate-run.test.py` `test_only_disk_blocking_stops_at_30_minutes`, `test_disk_beside_memory_keeps_90_minutes`, `test_an_unreadable_disk_probe_warns_once_and_never_blocks`).
  - **Heavy commands:** admission refuses a `capped.sh` command (normal priority) below a floor before it registers, with exit 74 and `admission: <id> refused: disk floor: <volume>: <values> (floors: ...); not started` on stderr. It reads the volumes of the admission state directory and the command's directory. Bounded jobs (high priority) are left to their own guard, a gate's prelaunch (`admission.test.sh`, "The disk floor").
  - **Queued commands:** a queued `capped.sh` command is checked again on every pass of its memory wait, so also at the moment it would be admitted. Below a floor it is refused the same way, with exit 74, and its entry is removed with a `refused` event, so its reservation is released and it never starts. That holds for each way a volume falls below a floor: the metadata headroom, the unallocated space under low headroom, and free data (`admission.test.sh`, "is refused while memory is still held").
  - **Unreadable probe, at entry and on each pass:** a part the probe cannot read, a crash and a 10 s timeout each print `admission: <id>: disk floor: warning: ...; not checked` once per reason for the command, not on every pass, and never refuse; a floor read beside an unreadable part still refuses (`admission.test.sh`, "entry, ..." and "queued, probe failures" / "queued, warned at entry").
  - **Exit 74:** sysexits' `EX_IOERR`, from `disk_guard.py check` and admission alike; `capped.sh` (root's, in `$EP_ORCH`) must pass it through with its own `74)` case. 75 already means a provider usage limit for worker runs and a busy WIP slot.
  - **Only refuses:** the guard never cleans, prunes or compresses anything.
- **Thresholds come from MAIN:** the driver and the monitor a gate runs are MAIN's, so a change to these values first applies to the gate after the one that lands it.
- **A stop after landing:** `land.sh` is the queue's last step inside the monitored unit, so the floor stop (or any in-run stop) can come after it moved the integration branch. Collection then fails on `noStoppedAttempt`, nothing completes, and the result is `stopped`, never `landed`, with `mainAtCandidate` and its **MAIN** line saying the integration branch moved (`gate-monitor.test.py` `test_the_floor_stop_still_fires_on_the_row_that_first_sees_the_receipt`, `gate-operator.test.py` `test_a_floor_stop_after_landing_fails_collection_and_records_main_at_the_candidate`, `gate-run.test.py` `test_a_floor_stop_after_landing_reports_stopped_with_main_at_the_candidate`).
- **Launch:** the operator passes the cap to `bounded.sh` as `BOUNDED_GATE_MEMORY_MAX`, which accepts only `15G` or `10G` (unset means `15G`; any other value, or the variable for another kind, is refused). An ambient `BOUNDED_GATE_MEMORY_MAX` is an injected override.
- **Mismatch:** a unit whose `MemoryMax` is not its mode's cap stops the gate as a cap mismatch.
- **Slice stop:** the slice-wide real-memory stop stays at 15 GiB in every mode.
- **Workers and admission:** 3-worker gates no longer fit; `gate-2` admission is unchanged.
- **Driver unit:** kind `driver` keeps `MemoryMax=2G`. The retained entry's `resume`, and so collection, runs inside it. Until 2026-11-07 every observer row in `resource-progress.jsonl` carried every ref (about 1 MB on this repository), so a long local suite's file ran to gigabytes (2.59 GB, 2,553 rows, for the waves 1-2 correction gate, whose driver the whole-file read OOM-killed on 2026-11-06). From then rows carried only the protected refs and a digest of the rest (about 23.5 KB of refs per row here), and since gate-ref-digest a digest of each set and the refs that moved (about 0.2 KB per row; [row evidence](#protected-refs)). Collection streams it one row at a time, keeping only each row's guard record for the cleanup check: a 2.98 GB synthetic file collects under a 2 GiB address-space limit at 52 MB peak RSS.
- **Replace evidence:** a replace gate's whole local sequence, in queue order with the real e2e preflight, peaked at 6.55 GiB kernel (6.59 GiB with reclaimed cache added back) and 5.16 GiB real. Each Node process it runs without a heap flag used at most 93 MiB of the 2,096 MiB default heap that Node picks below 15G. A cold-cache proxy (installs that copy instead of hardlinking) reached at most 8.13 GiB (`$EP_ORCH/mvp-20261023/replace-gate-cap-measurements.md`). Root qualifies the 10 GiB cap on the first replace gate. Evidence, monitor provenance and the monitor's qualification authority with its limits: [qualification](../orchestration-reference/qualification.md#monitor-qualification-authority).
