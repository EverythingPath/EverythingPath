# Gate modes: rule detail

Reference for the optional `gate.json` modes in [operations](../orchestration/operations.md). The operations file says when to use each mode and what to do on a refusal; this file is the exact rule each one enforces, as implemented in `scripts/orchestration/`. Read it when a mode refuses for a reason the summary doesn't explain, or before changing one of these scripts. Root's qualification plans for each mode are in [qualification](qualification.md).

## Remote heavy checks

Owner, 2026-10-30 (`$EP_ORCH/mvp-20261023/owner-decision-20261030-remote-heavy-checks.md`): a verified Boat run of typecheck, lint and the full suite for the exact candidate tree may count for the landing gate. `scripts/orchestration/remote_checks.py` is the verifier; its tests are `remote-checks.test.py`.

- **Publication:** Boat creates `$EP_ORCH/remote-checks/<runId>/` (create-only; `runId` matches `^[a-z0-9-]+-\d{8}-\d{6}-[0-9a-f]{6}$`), writes the logs and `full.json`, writes `manifest.json` (`remote-heavy-checks-v1`) last and then `chmod -R a-w`. Boat writes nothing else under `$EP_ORCH` and never edits the repo, wrappers, locks or policy. The orchestrator, not Boat, names a manifest in `gate.json`.
- **Tree-only CI commits** (owner 2026-11-02, `$EP_ORCH/mvp-20261023/owner-decision-20261102-tree-only-ci.md`): root publishes a candidate with `scripts/orchestration/gate-push.sh <REVIEWED> <BASE> <label>` (tests: `gate-push.test.sh`): a parentless `git commit-tree` of `REVIEWED^{tree}` whose message carries the trailers `Gate-Reviewed`, `Gate-Base` and `Gate-Tree` (full SHAs; dates are `REVIEWED`'s committer date, so the same inputs give the same commit), pushed to that one checked URL, named in the push rather than `origin`, as `<commit>:refs/heads/gate/<label>` and no other refspec, never `--all`, `--mirror` or tags. It refuses, before reading anything, a set `GIT_CONFIG` (any value, empty too: only `git config` honours it and a selected file skips `include.path`, so the URL checked could differ from the one pushed; `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_COUNT`/`KEY_<n>`/`VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `HOME` and `XDG_CONFIG_HOME` apply to both and are allowed), then abbreviated SHAs, `REVIEWED` not descending from `BASE`, a dirty worktree (every untracked file whatever `status.showUntrackedFiles` says, a failed `git status`, or an index entry marked assume-unchanged or skip-worktree), an `origin` without exactly one push URL (with two, one could accept the push while the other refuses it; the values of `remote.origin.pushurl`, else `remote.origin.url`, are read NUL-separated, and one that is empty, starts with `-` or holds a control character, newline and CR included, is refused), a `url.<base>.insteadOf` or `pushInsteadOf` rewrite that applies to that URL or has no value, a remote named by that URL (`git push <url>` would use its URLs instead) and any tree file of 100,000,000 bytes or more, naming each. The integration branch and its history are never pushed; GitHub sees only the candidate's current files. CI checks the commit out with `fetch-depth: 1`; `remote_ci.py probe` (the job's first step, also in the run summary) and the manifest's `source` record the commit, its tree, its parents read from the raw commit object (a shallow clone hides them from `rev-parse`), its message and every trailer Git parses from it, and the job stops before any command on a checkout that is not clean or a commit that `remote_checks.gate_commit` refuses: parents, or a message whose trailers are not exactly the three. The trailer block is the message's last paragraph, every line `Key: value`; any other key there (another `Gate-*`, any case, or a non-gate trailer), a repeated key, a value that is not a full SHA, a missing trailer, a non-trailer line in the block or a gate key anywhere else in the message is refused, as is a `Gate-Tree` other than the tree. The gate host applies the same check to the recorded message and requires the recorded trailers to be the message's.
- **Runner** (owner 2026-11-06, replacing root's Blacksmith runner of 2026-11-03): every gate job in `ci.yaml` runs on GitHub's free `ubuntu-latest` (4 vCPU, 16 GB for this public repository) and logs `nproc`, `lscpu` and `free -g` before its work; the light `checks` job is unchanged.
- **Shards** (owner 2026-11-06, speed-ci-shards): the suite runs as N parallel `remote-shard` jobs (matrix `index: [1..N]`, fail-fast off, N=11 since fix r1), each `remote_ci.py shard`: `ARGV['suite']` plus `--reporter=blob`, `--shard=i/N` and absolute `--outputFile.json` and `--outputFile.blob`, under the pinned environment. Vitest's sequencer is `tests/shard-plan.ts` (fix r1): with `--shard`, shard 1 holds exactly the files that launch Chromium (only shard 1 installs it), and shards 2..N take every other file by longest-processing-time over the recorded per-file durations in `tests/shard-weights.json` (`scripts/orchestration/shard_weights.py RUN_DIR` regenerates it from a fetched green run; files under 5 s weigh the default). Every job sees one checkout, so each file lands in exactly one shard; runs without `--shard` keep Vitest's order. `remote-static` runs `remote_ci.py static` (install, typecheck, lint and `pnpm -s test:workflow`, stopping at the first failure; see **Static job** below). Each job checks out the gate commit and runs the shared setup `.github/actions/ep-setup` (the probe, pnpm, Node.js, the store fetch, the hardware log), then uploads its part (`remote-shard-<attempt>-<i>`, `remote-static-<attempt>`, named for the run attempt: its rows and its facts: commit, tree, root, status, toolchain, environment, environment keys, installed lock, runner with the GitHub run id and attempt) even on failure. `remote-checks`, the assemble job, `needs` both with `if: always()`: it installs offline, downloads only its own attempt's parts, records GitHub's `needs` results for both producer jobs as `producers`, copies the static logs to the run directory's top, each shard's log and JSON report to `shards/` and its blob to `blobs/blob-<i>.json`, runs the merge (`ARGV['suite']` plus `--merge-reports=<run>/blobs` and `--outputFile.json=<run>/full.json`) and writes the manifest last with `static` and `shards` beside the four command rows, recording every part as it came. Vitest's merged JSON report has the single run's shape and counters and is exactly its shards' composition (a real two-shard merge in `remote-checks.test.py` `MergedReportTest`), except that its snapshot summary is always empty, since Vitest fills it only while tests run.
- **Shard bindings** (fix r1: one rule, the merge is its shards by construction): every manifest has `shards` and `static` (the single-job shape is refused outright, however reached), and the suite row's argv is the merge. `shards` holds exactly the indexes 1..N of one N (all `--shard=i/N` agree, none repeated, none missing, in order), each with canonical argv, an integer zero exit, timing, a log, a JSON report and a blob at `blobs/blob-<i>.json` (hashed, relative, regular, read-only); `blobs/` holds nothing else, because `--merge-reports` reads every file there. Each shard's and the static job's facts equal the manifest's (the assemble job's): the same checkout, toolchain, environment and keys, and installed lock, and the same GitHub run id and attempt in its runner (fix r1 on split B). `producers` is exactly `remote-shard` and `remote-static`, both `success`: GitHub's job result is authoritative, so a failed, cancelled or skipped producer refuses whatever parts were found, and an earlier attempt's part never stands in for a failed rerun. Each shard report stands alone: at least one test file and one test, then the remote suite's verdict (no snapshot write, all green but for listed host-audit skips, counters reconciled with its own assertions). The merged report then gets the same verdict with every listed test present, and must be exactly the shards' composition: no test file in two shards, the merged files exactly theirs, each with its shard's status and (ancestorTitles, title, fullName, status) multiset, and every counter the shards' sum. No report may list a test file twice. Verify, `replace`'s original suite and compare all judge through this one path (`remote_checks.suite`), and `verify_local` still compares the merged file set with the gate host's `vitest list --filesOnly`.
- **Static job** (gate-ci-workflow, speed-gate-review #5): `remote-static` runs install, typecheck, lint and then `pnpm -s test:workflow` (`scripts/orchestration/workflow.test.sh`, the orchestration suite's fixture contracts), stopping at the first failure. The fourth row is recorded like typecheck's and lint's (name, argv, exit, timing and a hashed `workflow.log`), but as the manifest's `workflow`, beside the four `commands` rows, because a verifier from before this slice pins `commands` exactly and must still accept the manifest. `remote_checks.workflow` checks the row whenever it is present: exactly a command row's keys, argv `pnpm -s test:workflow`, an integer zero exit, timing and its log. A failed run also fails the static job, so GitHub's `remote-static` result refuses it at any verifier. `test:workflow` runs on the runner from the depth-1 gate checkout: no `$EP_ORCH`, gate-host sources, git identity or user systemd. Its tests use only fixtures and scratch under `run_tmp`. A test that needs gate-host sources prints a `SKIP (host-only: …)` line naming the missing source, never a silent pass.
- **Widen then narrow** (speed-gate-review #4): a landing's manifest is verified by MAIN's verifier, the authority, and by the candidate's, which the queue runs, so it must satisfy both. A verifier or producer contract change therefore lands in steps. First widen: the verifier accepts both shapes. Then switch the producer, which can land together with the widening only when the old verifier still accepts the new shape. Finally narrow: require the new shape, in a later slice, once the widened verifier is MAIN's. A change that cannot be split gates in local mode; `compare` is no escape (see "Verifier and producer changes: widen, then narrow" below, the one rule). The same holds for `host-audits.json` (the candidate's script, MAIN's `bound_audits`). For the static job's `workflow` row: gate-ci-workflow widens (`REQUIRE_WORKFLOW = False`: a manifest with or without the row passes) and switches the producer in one landing, since the earlier verifier ignores the new key. The one-line follow-up on branch `t3/gate-ci-workflow-require` sets `REQUIRE_WORKFLOW = True` after that landing. `remote-checks.test.py` checks both settings, so the flip changes no test.
- **Host audits** (owner 2026-11-02, `$EP_ORCH/mvp-20261023/owner-decision-20261102-w1-host-audits.md`): the catalog provenance audits need sources only the gate host has (`~/repos/everythingpath/sources/{foundryvtt-pathfinder1,pf1-content,prd-2026-10-20}` and `~/repos/everythingpath/.ep-cache/pcgen-<pin>`), so they skip by their `skipIf` in CI, which runs plain `pnpm test`. `scripts/orchestration/host-audits.json` (`host-audits-v1`: `kind`, `sources`, `tests` as `{file, fullName}`, sorted and unique) pins exactly those tests and, since CI has no history, the tests that need it: `attribution-evidence-codec.test.ts`'s two tests that read historical blobs skip only when a blob is absent (the list's sources name the history). It was derived by running the whole suite with `HOME` pointed at an empty directory and collecting every skipped test, cross-checked against the `skipIf` sites; the two `win32` skips in `tests/local-convex-development.test.ts` are not in it, because the job runs on Linux and the verifier binds the platform to the gate host's. A test that starts needing a host source goes into the list in the same change.
- **Bindings:** source tree = `TREE` and the queue's `HEAD^{tree}`; the remote commit is parentless (`parents: []`) and its `Gate-Tree` equals that tree; `Gate-Base` = `BASE` and the queue's pinned base; `Gate-Reviewed` is a commit on the gate host whose tree is `TREE` and which descends from `BASE` (the operator also requires it to be `REVIEWED` or the prepared squash), so ancestry is checked locally, never from the remote; `source` has only `commit`, `tree`, `parents`, `trailers`, `message`, `status` and `root`, and the message's trailers are only the three, each once, as recorded; empty source status; `pnpm-lock.yaml`/`package.json` hashes equal the candidate's blobs and the installed-lock hash equals the worktree's after the queue's reinstall; `hostAudits: {file, sha256}` names `scripts/orchestration/host-audits.json` and its sha256 equals the candidate's blob; node, pnpm, platform and arch equal the gate PATH's; the effective `timeZone` equals the gate host's (Boat sets `TZ`); `CI=true`, `LC_ALL=C.UTF-8`, `VITEST_MAX_WORKERS=2`, no `NODE_OPTIONS` or other `VITEST_*`; only `GOMEMLIMIT` as a resource override; exact argv in the order install, typecheck, lint, suite; the `workflow` row, when present (required once `REQUIRE_WORKFLOW`), exactly a command row with argv `pnpm -s test:workflow`; integer zero exits and `completed: true`; an all-green suite (`success`, no failed or todo test, no failed or pending suite, every suite and file passed; Vitest 4 counts a file or suite of skipped tests as passed) with no snapshot write, where the only tests allowed to be skipped or pending are listed ones and every listed test is present (skipped or passed); the remote file set equals the local `vitest list --filesOnly`. Referenced files are hashed, relative, regular, read-only and inside the run directory. The exact format is in `remote_checks.py`.
- **Where:** `authorization()` verifies the manifest at every phase. The queue verifies it again after the pin (`remote.log`, record `remote-evidence/remote-verification.json`). In `replace` it then skips typecheck, lint and triage and runs `host-audits.sh` (`host-audits.log`): exactly the listed tests for the candidate commit, in a fresh `ep-gate-audits-*` checkout under `heavy.lock` inside the gate's bounded unit (without the light lane's read lock, like the rest of a `replace` gate), as `pnpm test <listed files> --testNamePattern=<one pattern anchored on the listed full names>` with the JSON reporter (Vitest 4 matches the describe titles and title, not the file). `remote_checks.py audit` requires Vitest exit 0, every listed test (every repeat) passed, every other test in those files filtered out (skipped), no other file and the remote suite's file and suite verdict, with the list equal to the manifest's; it writes `remote-evidence/host-audits.json` beside `host-audits-list.json` and `host-audits-report.json`. In `compare` the local full suite already runs the listed tests: the queue runs typecheck, lint and triage and requires the remote suite as `verify` judges it, the local suite all green under the same verdict, outside the list an equal (file, test, status) multiset, every listed test passed locally, and equal totals except that each listed remote skip moves one test from passed to pending (suite totals stay equal) (`remote-comparison.json`, which also references the list). Preflight, the identity checks and checked `land.sh` are unchanged. Collection adds `remoteChecks` and, in `replace`, `hostAudits` (the record re-judged from its list and report) or, in `compare`, `remoteComparison`; it takes `originalSuite` from the remote `full.json` under the same listed-skip rule in `replace`, references the manifest, logs and records, and records `suite: {source, manifest}` with source `remote+host-audits` (plus `hostAudits`, the record) or `local+remote-compare`; the completion scope names the remote suite and, in `replace`, the host audits. The script operator's result reports each suite's test files from its report's `testResults` (941 remote files and 13 host-audit files for TC1c) and Vitest's nested suite counters only as suites ([operations](../orchestration/operations.md#script-gate-operator) "Outputs").
- **Stop conditions:** A refused `gate-push.sh` (nothing is pushed), a CI checkout that is not a tree-only gate commit (the job stops before any command), a remote commit with parents, a missing, extra, repeated or abbreviated gate trailer (or a gate key outside the trailer block, or recorded trailers that are not the message's), a `Gate-Tree` other than the tree, a `Gate-Base` other than `BASE`, a `Gate-Reviewed` that is not the reviewed or prepared commit, unknown here, of another tree or not on `BASE`, a manifest of the W1 shape (`source.base`), a remote failure, a refused or stale binding (tree, base, lockfile, host-audit list, toolchain, timezone, environment, argv, completion, suite or file set), an unlisted remote skip or todo, a listed test missing from the remote report, in `replace` a host-audit test skipped, failed or missing on the gate host (or an unlisted test run, or a non-zero Vitest exit), or, in `compare`, any difference outside the list or a listed test not passed locally blocks landing; each has its own message, and there is no fallback to a local or partial pass.
- **Trust:** The manifest and its files are writable local artifacts pinned by sha256 in `gate.json` and the queue argv: this detects corruption, moved directories, stale scope and unsupported pass claims; it is not cryptographic attestation against an actor rewriting every file.
- **Curation:** a curation gate's candidate is its prep commit, kept rather than squashed, so `Gate-Reviewed` must be `REVIEWED` itself (no prepared squash widens it). `cur-prep.sh --remote-suite` runs every prep check except Vitest, records the plan and writes only `cur-<n>-prep.remote.receipt` (`tests=remote`). A curation spec with `remote` makes `gate_config.py` pin that file in `preservedEvidence` and refuse when it is absent (the local `cur-<n>-prep.receipt` is not pinned). At every authorization, `gate_core.curation_remote_scope` re-verifies the pinned sha256, parses the receipt strictly (each key once, `key=value` lines only, `result=ok`, `tests=remote`, `testLog=-`, `testLogSha256=-`) and requires its `issue`, `commit`, `tree`, `base` and `integrationBase` to be the gate's issue, `REVIEWED`, `TREE`, `BASE` and `BASE`. Submission and the queue reuse only that file (`prep_reusable … remote`) and refuse a missing or stale one instead of preparing again. Any amend of the prep commit, a message-only one included, needs a fresh remote-mode prep and push (v1). A conditional LAND binds as for code: the receipt and the manifest bind the repaired head `REVIEWED`. `rebaseProof`, `carriedReview` and `lane` stay code-only. Local curation prep plans are unchanged, and a curation gate without remote checks reuses only `cur-<n>-prep.receipt`, bound to its passing Vitest log.
- **Not supported:** pairs (`--pair`, `LAND_PAIR_MANIFEST`), more than one queue item and author validation receipts.
- **Resources:** a `replace` gate's unit cap is 10 GiB with a 16 GiB launch guard. `compare` keeps 15 GiB and 21 GiB, because it runs the local full suite. `gate-2` admission is unchanged in every mode. See [Gate memory](../orchestration/operations.md#gate-memory). The replace cap rests on measured kernel peaks: `catalog:pin` at 0.13 GiB with a 9 MB V8 heap, the writer check at 0.24 GiB, remote verification's local path at 0.14 GiB, the real e2e preflight at 0.21 GiB, the host audits at 4.79 GiB, codegen at 4.96 GiB, and the whole sequence at 6.59 GiB. Root qualifies it, with its wrapper change, on the first `replace` gate.
- **Timeouts:** GitHub's runner ran the suite 1.7–1.9× slower than the gate host in runs 41593918959 and 41596995308, and single tests up to 3.06× slower. With `CI=true`, `vitest.config.ts` gives tests and hooks 120 s. A test that needs more sets its own limit: at least 3× its slowest CI duration.

## Verifier and producer changes: widen, then narrow

A gate verifies its evidence twice, so a landing needs evidence that both verifiers accept.

- **Candidate's verifier:** `freeze` copies the candidate's `scripts/orchestration` into `queue-snapshot`. So the landing queue's `land-queue.sh`, `cur-land.sh`'s `remote_checks.py verify` and `host-audits.sh` are the candidate's. This runs the new queue code end to end.
- **MAIN's verifier:** `gate_core.verify_remote_checks` and collection's `remoteChecks` and `hostAudits` checks run at `BASE`. MAIN's is the authority, so a candidate cannot weaken its own check.
- **Rule:** a change to a verifier, or to the producer of gate evidence, lands in two steps:
  1. widen: the verifier accepts both the old and the new shape, and the producer keeps the old one, unless the old verifier already accepts the new shape (an additive key it ignores, such as the static job's `workflow` row), in which case the producer may switch in the same landing;
  2. narrow, once step 1 is on MAIN: the producer switches and the verifier requires the new shape.
  A verifier is `remote_checks.py` (the manifest) or `bound_audits` (`host-audits.json`). A producer is the CI workflow that writes the manifest, or `host-audits.sh`. A change that cannot be split gates in local mode instead, where no remote manifest is verified. `compare` is no escape: both verifiers still judge the manifest there, and only the suite source differs.
- **Example:** ci-shards-a r2 (2026-11-07) changed both at once. The candidate's verifier required a sharded manifest. The evidence was the single-job manifest that MAIN's verifier still required. The queue refused it ("Remote manifest is not sharded"), and collection failed `remoteChecks` and `hostAudits`. That lost a 71-minute prelaunch wait and a local re-gate.
## Mechanical-rebase proof

Owner, 2026-10-31, item 1 (`$EP_ORCH/mvp-20261023/owner-decision-20261031-process-overhead.md`): a rebase-only change is a mechanical check, not new reviews. A code gate whose `gate.json` carries `rebaseProof: {oldBase, accepted, acceptedTree}` (exactly these keys, full SHAs) accepts Standards/Spec reviews bound to `(accepted, acceptedTree)` as well as `(REVIEWED, TREE)`. NEW_BASE is `BASE` and HEAD is `REVIEWED` by construction; they are not restated.

- **Rule:** `gate_core.rebase_proof` compares plumbing raw tree deltas, `git diff-tree -r --no-renames --no-abbrev -z`, byte for byte with no normalisation. Both chains, `oldBase..accepted` and `BASE..REVIEWED`, are non-empty and linear with the same count; each commit pair has an equal delta (`c^ c`) and an equal message body; the net deltas `oldBase accepted` and `BASE REVIEWED` are equal. So every path the slice changes has the same old and new objects on both bases: `REVIEWED`'s tree is `BASE`'s with the accepted slice's blobs.
- **Where:** `authorization()` re-verifies the proof from Git objects at every call (prepare, submit, collect, complete and each periodic integrity pass), after checking the field's shape, the code kind and `accepted^{tree} == acceptedTree`. It precedes the attempt directory, so a refusal launches nothing. Without the field, reviews bind `REVIEWED`/`TREE` exactly as before, and the completion scope is unchanged; with it, the scope adds `reviews accepted at <accepted> on <oldBase> carried by the mechanical-rebase proof`.
- **Stop conditions, each with its own message:** a malformed field or a curation kind; an unmoved base (`oldBase == BASE`); a missing `accepted`/`oldBase` object; an accepted tree mismatch; `oldBase` not an ancestor of `BASE`; an empty or non-linear (merge) chain; a different commit count; a commit pair whose delta or message differs; a different net delta (overlap with the base movement or changed content); no review binding `accepted`. Any overlap between the slice and the base movement refuses, even a clean rebase: overlap means full independent reviews. There is no fallback to a normalised or partial pass.
- **CLI:** `python3 -B scripts/orchestration/rebase-proof.py WT OLD_BASE ACCEPTED NEW_BASE` (full SHAs) requires a clean WT whose `HEAD` descends from NEW_BASE, runs the same function and prints one JSON object: `{verdict: "PASS", oldBase, accepted, base, reviewed, commits, paths, tree, rebaseProof}` (exit 0), whose `rebaseProof` goes into `gate.json` as is, or `{verdict: "FAIL", reason}` (exit 1). `--head SHA` reads objects only and skips the clean-worktree check. It writes no files; the operator does not import it.
- **No chain:** after repeated rebases, prove from the original accepted commit on its review base straight to the current head. Keep `accepted` reachable with an archive ref (for example `refs/archive/RUN/<slice>/accepted`); a missing object refuses.
- **Trust:** verified from Git objects at every authorization; the full gate suite remains authoritative for semantic interaction (the base changing something the slice calls), which no textual proof can see.
- **Not supported:** curation (refused), pairs (they do not use this config) and overlap. A review of a content-different earlier commit (owner item 2) is carried only by a [single-axis fix review](#single-axis-fix-review).
## Single-axis fix review

Owner, 2026-10-31, item 2 (`$EP_ORCH/mvp-20261023/owner-decision-20261031-process-overhead.md`): when only one axis had findings, only that axis re-reviews the fix; the other axis's LAND stands unless the fix touches behaviour it judged. A code gate whose `gate.json` carries `carriedReview: {axis, commit, tree, attestation: {path, sha256}}` (exactly these keys; `axis` `standards` or `spec`; `commit`/`tree` full SHAs) accepts the carried axis B's review at the earlier commit E = `commit` together with the other axis A's fix review at the head H.

- **Frame:** if A binds `(REVIEWED, TREE)`, then H = `REVIEWED` and the frame base F = `BASE`; if `rebaseProof` is present and A binds `(accepted, acceptedTree)`, then H = `accepted` and F = `oldBase`. Otherwise A refuses with today's `Wrong reviewed scope: <A>`.
- **Rule:** `gate_core.carry_proof(root, F, E, tree, H)` uses plumbing only. E's object exists and `E^{tree} == tree`; `F..H` is non-empty and linear; E lies strictly inside it (not F, not H). It returns `{base, carried, head, paths}`, where `paths` is the sorted `git diff-tree -r --no-renames --name-only -z E H`. A's report (its reference verified) must contain the literal `E..H` with full SHAs. B must bind exactly `(E, tree)`; every other review check (task/run, terminal, identity, crossing the author model, independence, an unused rebase proof) is unchanged.
- **Attestation:** root writes one JSON file, referenced by `{path, sha256}`, with exactly `{version: 1, axis: B, carried: E, head: H, paths, statement, attestedBy}`. `paths` must equal `carry_proof`'s, so produce it from the same call (or `git diff-tree -r --no-renames --name-only -z E H`, sorted); `statement` (root's judgement that the delta stays within A's findings and touches no behaviour B judged) and `attestedBy` are non-empty strings.
- **Where:** `authorization()` checks the field's shape and the code kind, then, before the review loop, re-verifies the frame, `carry_proof`, A's report and the attestation at every call (prepare, submit, collect, complete and each periodic integrity pass). It precedes the attempt directory, so a refusal launches nothing. Without the field every check and message is today's, and the completion scope is unchanged; with it, the scope adds `; <B> review accepted at <E> carried over the <A> review of <E>..<H> by attestation <path>` after any rebase suffix.
- **Stop conditions, each with its own message:** a malformed field (`Invalid carried review`) or a curation kind (`Carried review is supported for code gates only`); A at neither frame head; a missing object; a carried tree mismatch; an empty or non-linear (merge) chain (`Carried review chain is empty or non-linear`); E outside the chain, including E = F and E = H (`Carried commit is not in the fix review's chain: <F>..<H>`); a report that does not name the full-SHA delta; an attestation reference or sha256 mismatch; an attestation key, value or path list that differs (`Carried review attestation mismatch: <key>`); B not bound to `(E, tree)`, including B at `REVIEWED` (`Wrong carried scope: <B>`, so an unused field refuses). There is no fallback.
- **Composition:** fix first, rebase last. Fix-then-rebase passes: A binds `accepted`, B binds E in `oldBase..accepted`, and the unchanged rebase proof carries the whole chain, E included, to `REVIEWED`. Rebase-then-fix refuses: with A at `REVIEWED` and E on the old base, E is outside `BASE..REVIEWED`, so `Carried commit is not in the fix review's chain` fires first (before `Unused rebase proof`); B then gets an ordinary delta review.
- **Trust:** Git objects, the report bytes and the attestation's keys and paths are verified at every authorization. The `statement`, and A's confirmation that the delta stays within its findings and touches nothing B judged, are recorded judgement, as with every review ("the parent supplies authentic observations"). The full gate suite remains authoritative for semantics.
- **Not supported:** curation (refused), pairs (`paired-gates.md` uses its own bindings) and rebase-then-fix (refused). A fix broader than the findings goes to both axes.

## Conditional LAND

Owner, 2026-11-04 (`$EP_ORCH/mvp-20261023/owner-decision-20261104-review-freeze-ci-conditional-land.md`): a review that answers "LAND once X is fixed" with a machine-checkable X needs no further review round once root has verified X. A code or curation gate whose `gate.json` carries `conditionalLand: {axes, commit, tree, paths, message, attestation: {path, sha256}}` accepts the reviews of `axes` at the reviewed commit E = `commit` together with the repaired head H.

- **Field:** exactly these keys. `axes` is a sorted, non-empty list of the kind's review axes (`standards`, `spec`; or `curation`). `commit`/`tree` are full SHAs. `paths` is the sorted, unique list of files the conditional named; `message` is `true` when it named the commit message. At least one repair is named.
- **Frame:** H = `REVIEWED` and the frame base F = `BASE`; with `rebaseProof`, H = `accepted` and F = `oldBase` (fix first, rebase last).
- **Rule:** `gate_core.conditional_proof(root, F, E, tree, H)` uses plumbing only. E's object exists, `E^{tree} == tree` and E is not H; `F..H` is non-empty and linear. Either E lies strictly inside it (`relation: "descendant"`: later commits make the repair) or E is an amend of H's tip (`relation: "amend"`: E's only parent is H's parent, as when a count or a curation prep commit's message is repaired in place). It returns `{base, commit, head, relation, paths, message}`: `paths` is the sorted `git diff-tree -r --no-renames --name-only -z E H`, and `message` is whether an amend changed the commit message (always `false` for a descendant, whose later commits carry their own messages).
- **Reviewed scope:** only conditional files grant scope (root, fix round 3: report Markdown is never parsed for scope). A reviewer who answers conditional LAND writes `<axis>-conditional.json` (curation: `curation-conditional.json`) next to the report, a JSON object with exactly `{version: 1, verdict: "land-once-fixed", reviewed: <full E SHA>, paths: [...], message: true|false, check: "<command or expected value>"}`; the review record binds it as `conditional: {path, sha256}` (gate spec: the review entry's `conditional`). `gate_core.conditional_file` reads it as strict JSON (a repeated key refuses): exactly those keys, `version` the integer 1, `verdict` exactly `land-once-fixed`, `reviewed` a full SHA equal to the review's bound `commit` and to E, `paths` a sorted list of unique non-empty repo paths, `message` a boolean, at least one permitted repair, and `check` a non-empty string. The permitted scope is the union over the listed reviews' files; a listed review without one is an ordinary LAND at E and grants nothing, and at least one listed review must bind a file. Only a listed review may bind a file. The repair's paths must lie inside that union, and an amend may change the message only when a file permits it (`Conditional LAND exceeds the reviewed scope`).
- **Exactness:** the configured `paths` must then equal the repair's paths, and `message` its message change. A broader delta, a path outside the named set, a named path the repair left alone, an unnamed message change and a named message repair that is absent all refuse.
- **Attestation:** root writes one JSON file with exactly `{version: 1, kind: "conditional-land", axes, commit: E, head: H, relation, paths, message, check: {command, output, commit}, statement, attestedBy}`. `relation`, `paths` and `message` equal `conditional_proof`'s. `check` records root's mechanical check of X: the command, its output (both non-empty) and the commit it ran at, which is `REVIEWED`, the commit being gated (after a rebase, rerun it on the rebased head). `statement` (root's judgement that the repair is X and nothing more) and `attestedBy` are non-empty strings.
- **Where:** `authorization()` checks the field's shape, then, before the review loop, re-verifies the frame, `conditional_proof`, the conditional files and the attestation at every call (prepare, submit, collect, complete and each periodic integrity pass), and `gate-run.py` runs the same check in its mode prechecks. The listed axes must bind exactly `(E, tree)` (`Wrong conditional LAND scope: <axis>`); every other review check is unchanged, and an axis not listed binds `REVIEWED`/`TREE` (or `accepted`) as before. With a rebase proof whose accepted commit no review binds, the conditional LAND's repaired head uses it. Without the field every check and message is today's. With it, the completion scope adds `; <axes> review accepted at <E> with a conditional LAND, repaired to <H> (<paths and/or the commit message>) by attestation <path>`.
- **Stop conditions, each with its own message:** a malformed field (`Invalid conditional LAND`); a combination with `carriedReview` (`Conditional LAND does not combine with a carried review`); a missing object; a tree mismatch; E = H (`Conditional LAND needs a repair`); an empty or non-linear (merge) chain (`Conditional LAND chain is empty or non-linear`); E neither inside the chain nor an amend of its tip, including E = F, a side commit and an amended merge (`Conditional LAND commit is neither in the chain nor amended at its tip: <F>..<H>`); a path or message mismatch (`Conditional LAND path mismatch`, `Conditional LAND message mismatch`); no listed review binding a conditional file (`Conditional LAND scope missing`); a file bound to a review conditionalLand does not list, or bound with no conditionalLand (`Conditional file bound to a review conditionalLand does not list`); a missing file (`Conditional file missing`); a changed file (`Evidence/input changed`); a binding that is not `{path, sha256}`, a file that is not one JSON object, a repeated key, missing, extra or unknown keys, a wrong `version` or `verdict`, a short `reviewed`, malformed `paths`, a non-boolean `message`, a file permitting nothing or an empty `check` (`Invalid conditional file for <axis>`); a `reviewed` other than the bound commit and E (`Conditional file for <axis> reviewed ...`); a repair outside the reviewed scope; a missing attestation file, a changed sha256, or an attestation key or value that differs (`Conditional LAND attestation mismatch: <key>`). There is no fallback.
- **Fail-open class (scope sources):** every input that could grant repair scope: the `conditionalLand` configuration (`paths`, `message`), root's attestation (`paths`, `message`), the review reports and the conditional files. Only the conditional files of listed reviews grant scope, bound by sha256 and read as strict JSON. The configuration and the attestation must each equal the repair, which must lie inside the files' union, so they can narrow the scope but never widen it. Report Markdown is never read for scope: verdicts, SHAs, headers, scope-like lines, fences, quotes, comments and JSON inside a report are all inert, so the round 2 and 3 routes (another commit's report naming E, a FIX FIRST report with a scope line, an open fence, a lazy blockquote, an open HTML comment) grant nothing. Refused set: as in the stop conditions above. What the gate cannot check is whether the permitted paths' content is X and nothing more, and whether the recorded check proves X: root's attestation records that judgement, as the single-axis attestation does. The full gate suite stays authoritative for semantics.
- **Not supported:** pairs, `carriedReview` together with it (refused), rebase-then-fix (E on the old base outside `BASE..REVIEWED` refuses) and a repair that changes a commit before the tip in place (an amend deeper than the tip refuses).

## Light landing lane

Owner, 2026-11-01 (`$EP_ORCH/mvp-20261023/owner-decision-20261101-no-unneeded-full-gates.md`): "dont run full gates when it is provably not necessary". **Basis, owner 2026-11-01 (`$EP_ORCH/mvp-20261023/owner-decision-20261101-light-lane-bounded-risk.md`): bounded risk.** The lane establishes that a full gate is *very likely* unneeded, not a strict proof. Every later code slice still runs the full gate on a tree that includes the change, so a dependency the lane missed fails that next full gate, and triage points at it. A reviewed, mechanical rule decides, never a reviewer's judgement. A code gate whose `gate.json` carries `lane: {mode: "light", rule: "light-lane-v1", paths}` (exactly these keys) skips codegen, the pin, typecheck, lint, the full suite and the E2E preflight. Identity, review binding (with `rebaseProof` and `carriedReview` unchanged), the exact-tree squash, the bounded unit, `impl_prep` (rebase, `pnpm install --offline`, writer check), `check:artifacts`, the checked `land.sh`, collect and complete still run. Research: `$EP_ORCH/research/light-landing-lane.md`.

- **Rule** (`scripts/orchestration/light_lane.py`, `verify(root, base, commit)`): computed from Git objects only (`GIT_OPTIONAL_LOCKS=0`, no working-tree read).
  - **R1 Shape:** the delta `git diff-tree -r --no-renames --raw --no-abbrev -z BASE C` is not empty, and every entry is A or M with mode 100644 on each present side. Deletions, renames (a D), symlinks, executables and submodules refuse.
  - **R2 Allowlist (default deny):** `AGENTS.md`, `CLAUDE.md`, `docs/standards.md`, `.claude/settings.json`, `.gitignore`; `*.md` at any depth under `docs/agents/`, `docs/product/` and `.agents/skills/`; `.claude/agents/<name>.md` at depth one.
  - **R3 Census** (`needles`, `needle_table`, `minimal_literals`, `grep_lines`, `census`): for each changed path the needles are (1) the full path with no name character `[A-Za-z0-9_.-]` on either side (`/` is a boundary, so `$repo/docs/...` is a hit); (2) the basename quoted or after `/`, closed by a quote; for each ancestor directory, (3) the ancestor followed by `/` and `*`, a quote, `$`, whitespace or the end, (4) the ancestor quoted alone, (5) the ancestor as a `{a,b}` member, and (6) for an ancestor of two or more components, the bare ancestor not continued by a name character or `/` (added after the base census found `curate.sh`'s `templates=$repo/docs/agents/orchestration/templates`). Each needle contains a literal (the path, the basename or the ancestor). The literals are reduced to a minimal set (a literal is dropped when it contains a shorter kept one, since a line holding it also holds the shorter one), and one `git grep -n -P -I -z` over their escaped alternation at C, with pathspec `. ':!*.md' ':!*.mdx'`, selects the candidate lines (Markdown, MDX and binary files are not searched); each needle's regex then decides on the lines that contain its literal. Every hit `(file, needle)` must be in `REFERENCES`, the reviewed table in `light_lane.py`: one reason per entry, keyed by file and needle, never by line. A `*` entry admits every needle in that file; there are seven, each with its reason: the rule's own `light_lane.py` and `light-lane.test.py`, the reader guard `tests/light-lane-reader-guard.ts` and its test and the read lock's test `scripts/orchestration/lane-lock.test.sh` (all three pinned by R4), and the two frozen hash manifests `tests/fixtures/spells-53{5,6}/preserved.json` (209 needle hits each; kept on disk until the #744 cleanup, and no check reads them or the paths they list, #749). The other entries are dispatch tools the queue never runs, comments, exclusion lists and temporary-repository fixtures.
  - **R4 Reader pins** (`BLOB_PINS`, `STAGE_IMPLEMENTATIONS`, `READER_GUARD`, `READ_LOCK`, `GLOBALS_PIN`, `SCRIPTS_PIN` in `light_lane.py`; `PINNED_AT` for all but `vitest.config.ts`, the guard and the lock files, which are pinned at the commits that added them): the blobs of `tsconfig.json`, `convex/tsconfig.json`, `vitest.config.ts`, `knip.jsonc`, `eslint.config.mjs`, `e2e/support/{source-files,source-evidence,workspace}.ts`, `vitest.setup.ts`, `tests/light-lane-reader-guard.ts`, `tests/light-lane-reader-guard.test.ts`, `scripts/orchestration/triage-failures.sh`, `scripts/orchestration/lane-lock.sh` and `scripts/orchestration/lane-lock.test.sh`; the skipped stages' implementations `scripts/catalog-pin.ts`, `src/lib/catalog/calculation-identities.ts`, `src/lib/catalog/runtime-compatibility.ts`, `scripts/orchestration/codegen.sh`, `scripts/local-convex/codegen.ts`, `scripts/lib/eslint-test-hygiene.mjs`, `scripts/check-eslint-suppressions.ts` and `scripts/lib/eslint-suppressions.ts` (`STAGE_IMPLEMENTATIONS`); a sha256 over the `src/styles/globals.css` lines matching `^@(source|import 'tailwindcss')`; a sha256 over the canonical JSON of the `package.json` scripts the stages run.
  - **R5 `.gitignore`:** compared as blob lines, never as patch text: both blobs must be UTF-8 text without a NUL byte (`.gitignore is binary or not UTF-8 text`), the old lines must be a subsequence of the new ones (only insertions; a removed, changed or reordered line refuses), and each inserted line is blank (spaces only), a `#` comment or a literal `.claude/` path (`^\.claude/[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*/?$`).
- **Light checks** (`light_checks`): a strict JSON parse of each changed `.json` (duplicate keys and `NaN`/`Infinity` rejected), and each relative Markdown link (`[text]` followed by a parenthesized target) on an added line of a changed `.md` (anchor stripped; `http:`, `https:`, `mailto:`, `#`, absolute, `$` and `<` targets skipped) must exist in C. Added lines are the new blob's lines that a line diff (`difflib`) of the old and new blobs inserts or replaces, numbered in the new blob; binary or non-UTF-8 Markdown fails. These are failures, not refusals: the full gate would accept the defect too, so the fix is a fix round.
- **The read lock (Vitest)**: every full gate that runs the suite locally runs every Vitest process of it under `lane-lock.sh`: `triage-failures.sh` wraps the full run and each rerun in its own disposable clean checkout (reruns of the feature head in `MAIN` are comparisons and stay unlocked; the owner's checkout is never chmodded). For exactly that process, every tracked regular file R2 allows except `.gitignore` (`light_lane.py lockable`) is mode 000, so any reader of one, in-process, a child process (`cat`, a spawned script) or another tool, gets EACCES and fails the full gate that adds it; lane-eligible files stay unread by the suite by construction. The list is taken and the checkout's own index refreshed before the lock, and no queue git command runs inside it; the locked process alone gets `core.trustctime=false` as `GIT_CONFIG_*` environment (never MAIN or the worker checkout, and never repository config, which a linked worktree shares), so git the suite runs compares stat data without re-hashing a file whose content and mtime are unchanged and only its ctime moved. The one such reader is `check:artifacts`, which `tests/catalog/launch-document.test.ts` runs; the light lane runs `check:artifacts` itself on every candidate, so that dependence on lane-file sizes is covered without the lock. The command runs in its own process group: when it exits, or on INT or TERM, the whole group gets TERM and, after a bounded grace (`LANE_LOCK_GRACE`, default 10 s), KILL, and the modes come back only once no process of the group is left; an unrestored mode, or a group that outlives KILL, fails the stage. Each run writes `lane-lock-<report>.json` beside its report (files, command, exit code, sha256 of the restored `<mode> <path>` lines); collection references them with the triage evidence. File contents never change, so the landed tree is the tested tree, and identity checks run on the candidate worktree, which is never locked. The in-process reader guard (`vitest.setup.ts`, `tests/light-lane-reader-guard.ts`, a Vite plugin in `vitest.config.ts`) stays as the fast, explicit diagnostic for in-process reads; R3 still covers literal references outside the suite.
- **The other skipped stages** (why skipping them is safe without a lock):
  - **Typecheck** reads what `tsconfig.json` includes (`next-env.d.ts`, `**/*.ts`, `**/*.tsx`, `**/*.cjs`, `**/*.js`, `.next/types/**/*.ts`; `.agents`, `agent`, `node_modules` excluded) and what `convex/tsconfig.json` includes (`./**/*` under `convex/`, `_generated` excluded), plus files a module imports by literal specifier. No allowlisted path is a code file or under `convex/`, and an import names its path (R3). Both configs are pinned.
  - **Lint**: ESLint lints `**/*.ts`, `**/*.tsx` (`eslint.config.mjs`, `.claude/**` ignored); knip's project globs are `*.{js,mjs,ts,tsx}`, `src/**/*.{js,ts,tsx,css}`, `convex/**/*.{js,ts}`, `scripts/**/*.{mjs,ts}`, `tests/**/*.ts`, `e2e/**/*.ts` (`knip.jsonc`). None matches an allowlisted path. Both configs and the lint scripts are pinned.
  - **Codegen** (`scripts/orchestration/codegen.sh` running `scripts/local-convex/codegen.ts`, both pinned) generates bindings from `convex/**`; no allowlisted path is under `convex/`.
  - **Pin** hashes the explicit `catalogCalculationV1Files` list (`src/lib/catalog/runtime-compatibility.ts`, read by `scripts/catalog-pin.ts`); a list names its files, so R3 sees any allowlisted one, and the `catalog:pin` script is pinned; `scripts/catalog-pin.ts` and its direct imports (`calculation-identities.ts`, `runtime-compatibility.ts`) are pinned too.
  - **E2E preflight**: `e2e-branch.sh` skips a candidate of only `docs/*`, `*.md` and test paths. Otherwise its reads of lane files are content-independent: `copyBuildWorkspace` (`e2e/support/workspace.ts:9-23`) copies every listed source file outside a dot path, so `AGENTS.md`, `CLAUDE.md`, `docs/agents/**`, `docs/product/**` and `docs/standards.md` are copied into the build workspace but not read by the build; `sourceFingerprint` (`e2e/support/source-evidence.ts:9-33`) hashes `AGENTS.md` and `.gitignore` into run evidence only (never a reuse key, #754). Both files are pinned, so a content-dependent change to either forces a full gate.
- **Why an R5 `.gitignore` line changes no skipped result**: `.gitignore` is never locked (git must read it); R5 is its proof. An added literal `.claude/...` line only adds ignore rules for paths under `.claude/`:
  - git `status --porcelain` and `ls-files --exclude-standard` (the identity checks in `cur-land.sh` and `e2e-branch.sh`, `listSourceFiles`): ignore rules affect only untracked files, so the line can only hide untracked files under `.claude/`; tracked files and the clean-worktree verdict of a checkout without untracked `.claude/` files are unchanged, and no stage creates files there.
  - knip: its project globs contain no `.claude/` path, so hiding `.claude/` files removes nothing from its inputs.
  - check-artifacts still runs in the light lane, so its reading of `.gitignore` is not skipped.
  - the e2e `listSourceFiles` copy: `copyBuildWorkspace` already skips every dot path, `.claude/` included, so the copied workspace is unchanged; `sourceFingerprint` already excludes `.claude/`, and its hash of `.gitignore` itself is evidence only.
  - Tailwind's scanner (in `globals.test.ts`) respects `.gitignore`, but `globals.css` already excludes `.claude` (`@source not`, lines pinned), so hiding more of it changes nothing.
- **Mechanically guaranteed:**
  - the allowlist (R2) and the shape (R1): no code, test, data, deletion, rename, symlink or executable lands through the lane, and no config except the two R2 names: `.claude/settings.json` (read only by Claude Code; strictly parsed as JSON by the light checks) and `.gitignore` (bounded by R5);
  - the pinned configs and implementations (R4): the typecheck, lint, Vitest and e2e configs, the `catalog:pin` script and its direct imports, the codegen entry, the content-independent e2e readers, the reader guard and the read lock; changing any of them refuses the lane until a reviewed re-pin;
  - the census (R3): no non-Markdown file names a changed path outside the reviewed table;
  - R5: `.gitignore` only gains blank lines, comments or literal `.claude/` paths;
  - the in-process guard: a Vitest test that reads a lane file through `fs` or a Vite load fails;
  - the Vitest read lock: in every full gate whose suite runs locally through `triage-failures.sh`, a suite process (or its child) that opens a locked lane file fails, and on every way out (exit, HUP, INT, QUIT, TERM) the lock stops its whole process group before restoring, so no process of the group runs with restored modes; a signal that arrives while the command is being launched, before its group id is recorded, is held and acted on right after, and nothing is restored in between. **Exception, a lock that dies before restoring:**
    - **When:** the lock process is killed by SIGKILL (for example the OOM killer, or a unit stopped without a grace period), or exits while the command is being launched and its group id is not yet recorded.
    - **What is left:** the lane files stay at mode 000, and the command (with any descendants) may still run.
    - **Scope:** only the gate's own disposable triage checkout (`../ep-gate-<worktree>-*`), which is the only checkout the lock is ever given; never `MAIN` or a worker checkout.
    - **Effect:** the suite run was cut short, so the gate has already failed and nothing lands.
    - **Record:** `lane-lock-<report>.json.active` beside the report in the triage evidence. It holds the checkout, every locked file with its original mode, the lock id (also in the command's environment as `LANE_LOCK_ID`) and, once known, the command's process group.
    - **Recovery** (the gate operator's job, as part of diagnosing the failed attempt before any fresh one; collection's `observedCleanup` check already fails on a leftover `ep-gate-*` checkout):
      1. Find leftovers by the record's group (`kill -0 -- -<group>`) or, without one, by its lock id (`grep -lz LANE_LOCK_ID=<lockId> /proc/[0-9]*/environ`).
      2. Kill that process group, or those processes (`kill -TERM`, then `kill -KILL`), and wait until none is left.
      3. Either restore each file's mode from the record, or simply delete the disposable checkout: `chmod -R u+rw <checkout>`, then `git worktree remove --force` or `rm -rf`. `triage-failures.sh`'s own exit cleanup already removes it when only the lock died. A gate with `remoteChecks` in `replace` mode skips local triage, so its suite runs without the lock (`compare` mode still runs the local suite under it);
  - the default path: without `lane`, the operator argv, the queue stages and logs, the result fields and the completion scope are today's; the only addition is the Vitest lock window and its records.
- **Not guaranteed (bounded risk, caught by the next full gate):**
  - adversarial or unusual readers: a test or script that reads a lane file's content through Git objects (`git show HEAD:<file>`), through `.gitignore` (readable by any process; R5 bounds only its ignore semantics), through a process outside the lock's group, or in a skipped-stage implementation beyond the pinned entry points (for example codegen's `scripts/local-convex/generate.ts`);
  - remote suites: a `remoteChecks` gate in `replace` mode takes its suite from the remote manifest and runs no local triage, so the lock does not apply to it; the remote protocol does not require the lock;
  - metadata: mode 000 leaves size, existence and directory listings observable, so a test asserting a lane file's exact size or presence is not caught. `check:artifacts`, which the lane runs, enforces the only size limits a lane file is checked against (the unbudgeted limits: a new file of at most 1,000,000 bytes, at most 5,000,000 bytes of growth and 50,000 added lines); a test's own size assertion is not one of them.
- **CLI:** `python3 -B scripts/orchestration/light_lane.py check ROOT BASE COMMIT` writes nothing and prints one JSON object: `{verdict: "PASS", rule, base, commit, tree, paths, references, pins, lane}` (exit 0), whose `lane` goes into `gate.json` as is, or `{verdict: "FAIL", reason}` (exit 1 for a refusal, 2 for a light-check failure). `verify WT BASE COMMIT EVIDENCE_DIR` runs the same checks for `cur-land.sh`, prints `light ...` lines and, on a pass only, creates `EVIDENCE_DIR/light-verification.json` (the result plus `passed: true`); an existing `EVIDENCE_DIR` refuses.
- **Where:** `authorization()` checks the field's shape, the rule, the code kind and the absence of `remoteChecks`, then re-proves the rule for `REVIEWED` on `BASE` at every call (prepare, submit, collect, complete and each periodic integrity pass); its tree must be `TREE` and its path list `lane.paths`. It precedes the attempt directory, so a refusal launches nothing. The operator passes `LAND_LANE=light LAND_LIGHT_EVIDENCE=<attempt>/light-evidence` after any remote argv. `land-queue.sh` refuses another value, `--pair`, more than one item, a curation item and `LAND_REMOTE_CHECKS`; `cur-land.sh` runs `light_lane.py verify` after the artifacts stage (`light.log`), then the final identity check and `land.sh`. Collection replaces `originalSuite` with `lightLane` (the record binds the rule, `BASE`, the squashed candidate, `TREE` and `lane.paths`, and the rule is re-proved for the candidate), references `light-evidence/*.json` and records `suite: {source: "none", lane: "light", rule}`. The completion scope becomes `Authorized light landing lane (every changed path is outside the full queue's pinned inputs under rule light-lane-v1, bounded risk, owner 2026-11-01; codegen, pin, typecheck, lint, the full suite and the e2e preflight not run) and checked completion only; no Cloud/GitHub/promotion qualification`, followed by any rebase and carry suffixes.
- **Stop conditions, each with its own message:** `Invalid lane: exactly mode "light", rule and paths`; `Light lane rule mismatch: <rule>`; `Light lane is supported for code gates only`; `Light lane does not combine with remote checks`; `Light lane refused: empty delta`, `<path> <status> mode <old>-><new>`, `<path> is outside light-lane-v1`, `<path> is referenced by <file>:<line> (<needle>)`, `reader pin changed: <name>`, `.gitignore removes or changes lines`, `.gitignore line is not a literal .claude/ path: <line>`; `Light lane path list mismatch`; in the queue, `unknown lane '<x>'`, `light lane does not apply to pairs`, `light lane binds one item`, `light lane is for code items only`, `light lane does not combine with remote checks` and `light lane refused (see <log>); not landing`. A refusal never falls through to the full stages: the operator writes a config without `lane` and runs a fresh full gate.
- **Trust:** Git objects at every authorization and again in the queue and at collection, under the bounded-risk basis above: what is not mechanically guaranteed is listed, and a missed dependency surfaces at the next full gate. Semantic interaction between code and docs does not arise, because a light candidate contains no code.
- **Not supported:** curation, pairs, `remoteChecks` and more than one item (refused); `README.md`, `GLOSSARY.md` and non-Markdown files under `.agents/skills/` (outside the allowlist until a reviewed rule bump).
- **Re-pin:** a `reader pin changed` refusal or a new census hit means the full gate now. Updating the rule (pins, allowlist or `REFERENCES`) is its own reviewed workflow slice, which must state why the changed reader still ignores the allowlist.

## Protected refs

Root, 2026-11-07 (gate-hold-scope): the monitor (`gate_monitor.py` `protected_ref`, `ref_violations`, `ArchiveLedger`, `other_ref_moves`) protects the gate's own refs in every gate mode and records the rest. Summary and what root no longer pauses: [protected refs](../orchestration/operations.md#protected-refs).

- **Snapshot:** preparation stores every ref in MAIN once, in `protected-refs.json` (bound in `prepared.json`), before it squashes. So it holds `BR` at its pre-squash commit and lacks a new `ARCHIVE`.
- **Rule per row,** over every protected ref in the snapshot, the row or the archive ledger:

  | Ref | Allowed value |
  |---|---|
  | `refs/heads/<BR>` | the prepared commit (`SQUASHED`) |
  | `refs/heads/<FEATURE>` | `BASE`, or `SQUASHED` after the checked fast-forward |
  | `ARCHIVE` | `REVIEWED` |
  | `refs/heads/main` | its snapshot value; absent stays absent |
  | any other `refs/archive/**` in the snapshot | its snapshot value (a rewrite or a delete stops) |
  | a `refs/archive/**` the snapshot lacks, in the first row that shows it | anything (an addition); the ledger keeps that value |
  | an archive in the ledger, in every later row | the value the ledger kept (a rewrite or a delete stops) |

  A ref outside the table is never judged. A violation is `{protectedRef, before, after}`: `before` is the snapshot value (for an added archive, its first observed value) and `after` is `null` for a deleted ref.
- **Archive ledger:** the rows of one attempt are judged in order through one `ArchiveLedger`, wherever they are judged. The live loop keeps one for its run. A restarted monitor first replays this invocation's rows already in `resource-progress.jsonl`, and a stop among them is its first row's stop. Collection's streamed scan keeps one over the whole file. An archive added and rewritten between two rows (5 s apart) is invisible to any sampling observer, as a move and its return on any ref is.
- **Automatic maintenance, per worktree** (root ruling, fix r2): Git resolves configuration per worktree at run time, so the check reads the effective values where a Git command would run, rather than parsing config sources.
  - **Worktrees:** `gate_core.maintenance_reading` lists MAIN and every worktree with `git -C MAIN worktree list --porcelain -z`. In each one it reads `git -C <worktree> config --get --type=int gc.auto` and `--type=bool maintenance.auto`. `--type` normalises what Git reads, so `yes`, `on` and `1` read as `true`, and an unparsable value exits 128. The values come from every layer and include Git applies there: system, user, the shared repository file, the worktree's `config.worktree` (with `extensions.worktreeConfig`), and `includeIf` `gitdir:` and `onbranch:`.
  - **Unresolved entries** (root ruling, fix r3): an entry Git cannot resolve is one of these:
    - one Git lists as `prunable`;
    - one whose directory went before or while it was read;
    - a locked one that is not yet a worktree of MAIN.

    Such an entry is `unreadable`, which is a refusal, unless it is one of the attempt's own scratch checkouts; those are recorded `absent`. The rule is strict because a worktree moved by hand (`mv`, locked or not) leaves exactly such an entry at its old path. It still runs Git, with its own `config.worktree`, on MAIN's object store at a new path that nothing lists.
  - **The attempt's own scratch checkouts:** they are known by exact path, never by name pattern.
    - The operator gives the gate unit `GATE_SCRATCH_WORKTREES=<attempt>/scratch-worktrees.txt`.
    - `triage-failures.sh` and `host-audits.sh` reserve their `ep-gate-*` directory with `mktemp -d`. They then append that exact path to the record with `paths.sh` `record_scratch_worktree`, before `git worktree add` creates the worktree. A path that cannot be recorded fails the script.
    - Each row reads the record as realpaths (`gate_core.scratch_worktrees`) after it takes the worktree list, and stores it under `maintenance.scratch`. Because a path is recorded before its entry exists, every own entry in the list is already in the record. Read before the list, a checkout created between the two reads would look foreign and stop the gate (Spec r4). The judge accepts an `absent` entry only at a path in that list, so collection keeps the rule.
    - The gate's own scratch checkout therefore passes while `git worktree add` creates it and while its cleanup removes it.
    - Nothing else passes: a manually moved worker worktree, an entry mid-creation that is not the gate's own, and an `ep-gate-*` directory nobody recorded all refuse. So does any stale scratch left by an earlier attempt, so root removes those before a gate.
    - Outside a gate the variable is unset and the scripts record nothing.
  - **A worktree added during the run** is read from its first row.
  - **Scheduled maintenance:** `maintenance.repo` is read with `git config --get-all --path` (so `~/` expands as `git for-each-repo` expands it) outside any repository, which is the scheduler's own system and user view, and in every readable worktree, which covers every layer and include. A refusal is an entry whose realpath is MAIN or a worktree, or a directory whose object store is MAIN's (a subdirectory or a symlink). Relative entries resolve against `$HOME`. Also refused: an active `git-maintenance@*` systemd user timer (`systemctl --user list-units --type=timer --state=active`) and a crontab line that runs `git maintenance` or `git for-each-repo`. A missing `crontab` binary or no crontab for the user reads as none. A reader that fails is `unread`, which is a refusal. All three are what `git maintenance start` installs on Linux.
  - **Refusals:** `maintenance_refusals` names each way maintenance can still run, prefixed with the worktree whose Git would run it: either setting unset, any value other than `0` and `false`, an unreadable value or worktree, a worktree list that failed, a reading without MAIN, or any scheduled run. A missing or malformed reading is a refusal too.
  - **Seams:** three use them. `gate-run.py`'s MAIN identity check (stage `identity`, and every later identity check) stops the driver before any input; the operator's prelaunch row (`observe` without an invocation, in `prepare`) refuses preparation; each observer row records the reading under `maintenance`, and a refusal there is an `automaticMaintenance` stop, in the live loop and at collection alike. Why all three settings: `maintenance.auto` stops the `git maintenance run --auto` that commit, merge, fetch, rebase and am start; `gc.auto=0` turns off every `git gc --auto` heuristic, `receive.autogc` included; scheduled maintenance (`git maintenance start`) runs the `maintenance.repo` entries regardless of `maintenance.auto`.
- **Row evidence:** `refs` holds the protected refs (about 20 KB here, almost all archives); `otherRefs: {count, sha256}` is the digest of the rest (`<object> <refname>\n` lines in refname order); `otherRefMoves: [{ref, before, after}]` appears only when a ref outside the set moved, appeared (`before: null`) or went (`after: null`) since the monitor's previous row. Its first row compares with the snapshot. Rows written before this change carry every ref under `refs` and are judged by the same table.
- **Identity, unchanged:** each row requires the candidate worktree clean at `SQUASHED` with tree `TREE`, MAIN clean at `BASE` or `SQUASHED` (with `TREE` once landed) and `ARCHIVE` at `REVIEWED`. The integrity worker's `check_identity` also requires the worktree on `BR`; a detached checkout fails its read. So another session's commit, edit or checkout in the gate's worktree stops the gate. Git itself refuses a second worktree on `BR`; a forced one can affect the gate only by moving `BR`, which stops it.
- **Threat model:** the maintenance check guards against accidental settings that ordinary worker activity leaves on: a worktree override, a branch include, a scheduled registration, or a value Git reads as on. That includes a worktree moved by hand, whose stale entry refuses, because its overrides would otherwise escape every read. Only the attempt's own recorded scratch paths may be unresolved. It does not guard against a session that sets out to evade it, for example by setting `GIT_CONFIG_*` or `-c` on one command, running maintenance by hand, or editing config between two rows and back. That is out of scope, and the HOLD rule covers it. **Residual window:** the check samples, so a change between two observer rows is live until the next row stops the gate. For example, a branch switch in a worker worktree can activate an `onbranch:` include that turns `gc.auto` on, and a commit made in that window can start automatic maintenance before the stop. The same window applies to a worktree override set between rows.
- **Not observable:** a manual `git gc`, `repack`, `prune`, `prune-packed` or `maintenance run`; the HOLD rule forbids them during a gate. `git worktree prune` is outside that rule: it deletes only `$GIT_COMMON_DIR/worktrees/<id>` entries whose worktree directory is gone (never a locked one), not objects or refs, so it cannot remove the gate's worktree while the gate can still pass (a missing worktree already fails every identity check). The gate's own cleanup runs it (`host-audits.sh`, `triage-failures.sh`), and the monitor could not tell a cleanup's prune from another session's, so the rule narrows to the object store rather than attributing prunes.
- **Which code judges:** the monitor and collection run the attempt's `operator-runtime`, which `freeze` copies from MAIN's checkout of `scripts/orchestration` (the operator's own directory), not from the candidate. A change to this rule is therefore judged at its own landing by MAIN's older rule, and takes effect for gates prepared after it lands. It needs no widen-then-narrow split: no candidate-side code reads `protected-refs.json` or the rows, and MAIN's rule for its own landing is the stricter one.
